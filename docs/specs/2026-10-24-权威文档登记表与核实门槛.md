- 来源：真实失败——项目迭代后 Agent 接到「更新 API 接口文档」，未找到最初文档而重新生成一份，同类文档多份并存、权威源随时间失效

## 意图（interview-me 确认，v2 终版）

- Outcome：为 vibe-base 增加「长期权威文档唯一权威源」机制——登记表 + 核实门槛：新建/更新权威文档前必先核实（查登记表为主，辅以全库检索）并显式报告核实结果；核实无命中 → 允许直接新建并同步登记，不强制停下询问。
- User：接入 vibe-base 的项目里的 Agent（规则消费者），与不再面对多份并存的用户。
- Why now：真实失败——Agent 更新 API 接口文档时没找到旧文档，重新生成了第二份。
- Success：任何权威文档任务，Agent 必然先核实并报告命中情况；已登记的权威文档必然命中（查表，不靠检索运气）；新建即登记，登记表随使用收敛。
- Constraint：AGENTS.md ≤100 行；根目录与 `skills/vibe-base/assets/` 成对同步；是 2026-10-23 决策门槛在文档域的对应物；登记成本每份一行。
- Out of scope：progress/memory 等按日期命名的易逝文档；机械 lint/CI 工具；存量文档一次性全量清点（首次触及时补登）。

## 机制形态裁决（登记表 vs grep）

用户判定规则：表与 grep 相比有明显优势才引入。评估结论（论据全文见关联决策记录）：

1. grep 原理上无法证明「不存在」——没搜到 ≠ 不存在；免询问授权（核实无命中可新建）只有建立在确定性查表上才安全，grep-only 会原样复刻本次事故。
2. 表把失败从能力域（遵守规则仍 miss，静默不可检）移到纪律域（漏登是可 grep、未来可 lint 的不变式）。
3. 表不取代 grep：核实 = 查表 + 全库检索双动作，grep 降级为兜底。
4. 形态取最轻：复用既有 design/specs README 扩为索引节，不新建文件、不造新概念；撤表 = 删索引行。

## 功能描述

做什么：AGENTS.md §6 同步规则增「权威文档唯一」一条并改写既有索引行；`docs/design/README.md`、`docs/specs/README.md` 增「权威文档索引」节（模板正本成对同步，模板侧为占位行）；既有权威文档同批补登。

不做什么：不加门禁脚本；不建集中式登记表新文件；不管 progress/memory 易逝文档；不做存量全量清点。
