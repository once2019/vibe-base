# 产物规范补「新增守卫的准入」：三问 + 责任归属

- 日期：2026-11-19
- 状态：已生效
- 相关模块：`AGENTS.md` §3、`docs/governance/coding-discipline.md`

## 决策内容

`coding-discipline.md` 新增一节「新增守卫的准入」：任何新增检查（门、断言、对账表、棘轮、体检项）先过三问——防的真实故障发生在哪一次运行、用户看不看得见、能否改成结构或测试；并按责任归属决定位置（内部一致性→测试，外部输入→运行时检查，偏好→提示词，开发者遗忘→`tests/` 或 CI）。

`AGENTS.md` §3「不推断未登记的集合」补一句边界：登记表若防的是「开发者忘记同步」而非「正确性依赖调用方」，归 `tests/` 或 CI，不进产品路径。

## 选择理由

来源是 storyboard-maker 的实测盘点（`docs/design/gate-and-generator-inventory.md` §六）：该项目根提交是纯治理骨架，首个代码提交与 `pipeline/gates/` 同批落地，结果是 93 个门、22 个诊断类型、78 个写端点对账表、mypy 棘轮、已退役的契约哈希——治理层的形状渗进了产品层。

机制本身大多是对的（每条门都能指出它防的真实故障），问题在准入门槛：只要「怕以后出错」就能加一条检查。这条对任何项目成立，不是分镜特有，所以收进技能而不是留在项目里。

§3 那句话被扩大解释了：「不推断未登记的集合」本意是不要依赖调用方补全上下文，实践里被读成「任何新增都要有登记表」。加一句边界把两种登记分开，成本一行。

## 被否决的替代方案

| 方案 | 否决原因 |
| --- | --- |
| 只留在 storyboard 的 design 文档 | 判据通用（任何项目的任何新增检查都适用），留在项目里下一个项目要重新推导 |
| 把三问做成 lint / 测试强制 | 第 1 问（故障发生在哪次运行）无法机械判定，强制只会得到填空式理由 |
| 顺带把 `coding-discipline.md` 按过程/产物拆文件 | 拆分是整理，不改变执行面；本次只补缺口，拆分另议 |

## 影响范围

- 涉及文件/模块：`coding-discipline.md`（新增一节）、`AGENTS.md` §3（两行）
- 兼容性影响：无代码变更；已初始化项目同步这两处
- 后续约束：新增检查在提交信息或设计文档里回答三问；「流程登记」类机制不进产品路径
