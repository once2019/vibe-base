# 主管侧缺陷重跑用 `--infra`，不占尝试配额

- 日期：2026-11-19
- 状态：已生效
- 相关模块：`scripts/foreman.py`（`cmd_dispatch`、`brief_text`）、`docs/governance/orchestration.md`（重派阶梯）

## 决策内容

`dispatch` 增 `--infra "<根因>"`：主管侧缺陷（验收命令写错、新树缺 `.env`/`.venv`、scope 漏登记）导致的重跑，
不推进 `task["attempts"]`、不被 `max_attempts` 拦住；派工单的「重派说明」标「主管侧修正重跑，不计入尝试次数」。
只接受 `failed` 状态，与 `--retry-note` 二选一。配额已满时须先 `task unblock --reason` 由人类确认，再 infra 重跑。

同时修一处编号错误：派工单「第 N 次尝试」原先写 `attempts + 1`，重派时多算一次（T-085 实际第 2 次、派工单写第 3 次）。

## 选择理由

storyboard 的 20 个多次派工任务里，6 个（30%）是主管侧缺陷造成的假 FAIL：T-027 的 `&&` 链没包 shell、T-028 缺 `.env`、
T-030/036/038/059 的 scope 漏登记。这些打回里 worker 的代码方向从未被否，retry-note 都写着「零代码改动，直接重跑验收」。

代价有两层。直接代价是白烧一轮 20–40 分钟（停 worker、重新派、重新探索）。更严重的间接代价是配额：T-027 派了 4 次，
前三次全是主管侧问题，第三次用完 `max_attempts` 就把任务判进 `blocked`，而真正该问的「任务是不是拆大了」根本没到点上。

计数口径应该反映「worker 试错了几次」，而不是「派工了几次」。

## 被否决的替代方案

| 方案 | 否决原因 |
| --- | --- |
| 主管自己改代码，不重派 | 主管不写业务代码是分工红线；且改动仍需验收与留证 |
| 复活原 worker 会话继续（`pi -c`） | 判断性错误时作者会为原方案辩护，写与审分离的价值就没了；infra 场景虽无此风险，但两套恢复路径成本高于收益 |
| infra 直接从 `blocked` 放行 | blocked 是「交人类」的语义，允许造成 block 的人自己绕过等于取消这道门 |
| 不区分原因，只把 `max_attempts` 调大 | 掩盖问题：真正的三次失败该转 blocked，调大只会让坏任务多跑几轮 |

## 影响范围

- 涉及文件/模块：`foreman.py`（参数、校验、attempt 编号、brief 标签）、`orchestration.md` 重派阶梯、测试 4 项
- 兼容性影响：`dispatch` 行为对不传 `--infra` 的调用完全不变；已初始化项目需同步脚本与文档
- 后续约束：`--infra` 必须写根因（进事件日志可审）；把真实失败标成 infra 属滥用，审查时看 reason 是否成立
