# 权威文档登记表与核实门槛

- 日期：2026-10-24
- 状态：已生效
- 相关模块：`AGENTS.md`、`skills/vibe-base/assets/AGENTS.md`、`docs/design/README.md`、`docs/specs/README.md`

## 决策内容

长期权威文档（架构/接口/规格类）同类全库唯一：新建/更新前先核实——查所在目录 README 索引（辅以全库检索）并在回复中报告核实结果；未命中可直接新建，但新建即在索引登记一行；散落他处的存量同类文档首次触及时补登。design/ 与 specs/ 的 README 扩为权威文档索引；progress/memory 等按日期命名的易逝文档豁免。

## 选择理由

- 解决的问题：实测失败——「更新 API 接口文档」任务中 Agent 未找到最初文档而新建第二份，权威源失效。成因：权威源位置只存在于文件系统里靠搜索发现，而搜索无法证明「不存在」，Agent「核实过、没找到」即合规地制造了重复。
- 用户判定规则「表对 grep 有明显优势才引入」的裁决：① 免询问门槛（核实无命中 → 直接新建）的授权只有建立在确定性查表上才安全，grep-only 即原事故复刻路径；② 表把失败从能力域（守规仍 miss、静默不可检）移到纪律域（漏登是可 grep、未来可 lint 的不变式）——把不可检测的失败换成可检测的失败；③ 表不取代 grep，核实=查表+全库检索双动作。
- 约束：L1 预算 88/100 行——新增 1 条同步规则行并改写既有索引行（落地后 89/100）；登记成本每份一行，不复发 2026-10-22 撤销的台账成本。
- 可逆性：删 §6 该条 + 两 README 索引节即撤销，分钟级。

## 被否决的替代方案

| 方案 | 否决原因 |
| --- | --- |
| 只加行为规则（全库检索 + 新建前报告，不建表） | 无法证明「不存在」，免询问授权下即原事故复刻路径；纪律合规但能力性 miss 静默发生、不可审计 |
| 未登记时停下询问而非新建 | 用户否决：沟通成本；有确定性查表后「无命中」已是可靠证据，询问多余 |
| 集中式登记表新文件 | 与 §6「每类信息各就各位」冲突，目录 README 已是自然落点，新文件属不必要的新概念 |
| 机械 lint/CI 检测重复文档 | 与 2026-10-22 复盘决策否决理由相同（门禁成本与误报）；权威文档数量少时成本收益倒挂，留待文档泛滥后再议 |

## 影响范围

- 涉及文件/模块：`AGENTS.md` §6（与 assets 成对）、`docs/design/README.md`、`docs/specs/README.md`（根=实况行、模板=占位行，受控分歧形态同 `decisions/README.md` 先例）、`SKILL.md`（版本 bump）
- 兼容性影响：无破坏性变更；既有权威文档本批补登（design 1 份、specs 2 份）
- 后续约束：新建权威文档必须同批登记索引；更新任务必须先查表并报告核实结果；易逝文档（progress/memory）豁免
