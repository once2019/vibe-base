# 门失败不等于任务失败：三问放行 + 准入加泛用性

- 日期：2026-11-19
- 状态：已生效
- 相关模块：`AGENTS.md` §2/§3、`docs/governance/coding-discipline.md`（守卫的生命周期）、`scripts/foreman.py`（派工单红线与 DONE 要求）
- 修订：`2026-11-19-guard-lifecycle` 的「举证」条款与其「准入三问」（见该记录追记）

## 决策内容

**1 门失败先判影响面，三问全否就继续交付：**

| 问 | 否的含义 |
| --- | --- |
| 这次失败会改变下游产物吗？ | 消费方拿到的还是同样的东西 |
| 会产生用户可见的错误结果吗？ | 产物在目标平台上仍然可用 |
| 会掩盖另一个真实缺陷吗？ | 不是把真问题盖住了 |

全否：把门名、失败原因、判了哪三问写进交付说明与遗留项，继续做。任一为是才按分档处理（归一 / 回喂重试 / 阻断）。安全、数据破坏、不可逆动作不在三问范围内，仍然硬挡。

**2 举证改为「记录后继续」：** 指不出真实故障、或条件里只有当次输入字面量的守卫，记一行偏差后继续，不停下等裁决。

**3 准入加第四问（泛用性）：** 判据对这类输入普遍成立吗？条件里出现当次输入的字面量、单次特例、某个项目号，就是按这一次拟合的，改成归一或删掉。

偏差的记录位置是 DONE 正文与竣工单遗留项，不新增 `task.json` 字段。

## 选择理由

规则文本的比例先失衡了：改前技能文档里「不许/禁止/必须/不得/一律」78 条，「遗留/可接受/记录后继续/不影响」7 条，11:1。规则只朝一个方向写，Agent 学到的默认动作就是加门与停工。

三条文本直接造成两个后果：

- 「提交前上述检查必须全部通过」+「举证不许自行放宽或就地绕开」= 遇到不合理的门时唯一合法动作是停下。没人要求任务完成，只要求检查全过。
- 「每条规则必须可判定」把判断类规则改写成检查，而准入三问只问「防哪个真实故障」，没有一问问「这类输入都成立吗」，于是门按触发它的那一次输入拟合。测试没出现过的正常输入就能卡住。

改后比例 75/12（6.3:1），剩余差距来自尚未落地的「自审分级」与「完成定义改口径」。

## 被否决的替代方案

| 方案 | 否决原因 |
| --- | --- |
| 加一条「不要过度设计」的规则 | 用门治门的病，会变成第 79 条绝对陈述，且它本身不可判定 |
| 直接删掉不合理门 | 一次上报就能拆掉防真实故障的守卫；先记录、事后由主管裁决 |
| 把三问写进 `task.json` 新字段 | 没人读的字段等于没记；交付说明与遗留项已经承载同样的信息 |
| 只改派工单不改 L1 | 单会话模式只读 `AGENTS.md` 与细则，不改等于只修了派工路径 |

## 影响范围

- 涉及文件：`AGENTS.md`（§2 规则 + §3 守卫边界）、`coding-discipline.md`（准入四问、举证改写、新增「门失败不等于任务失败」）、派工单红线与 DONE 要求、测试 3 项
- 兼容性影响：无状态机与命令变更；worker 侧多一条「不许默认停工」
- 后续约束：新增守卫必须过四问；门失败先答三问；安全与不可逆动作不走三问
