# 校验的降级阶梯：归一 > 回喂重试 > 阻断

- 日期：2026-11-19
- 状态：已生效
- 相关模块：`docs/governance/coding-discipline.md`（新增守卫的准入 · 退出与降级）

## 决策内容

`coding-discipline.md` 的「新增守卫的准入」补一级下游：校验拦住违规后怎么处理，按三类分档。

- **语义唯一、只是词汇或形态不同**（同义词、简写、全半角、别名）→ 归一，不重试。
- **语义错误，必须模型理解后才能改**（人物不在名单、拍号丢失、台词不符、秒数越界）→ 回喂重试，reason 给出期望值。
- **阻断**只留给「平台会拒 / 产物必崩」。

再配四条判据：能一一映射的差异不重试；同一项连续成为唯一致败原因就改提示词或加归一；长期零触发的进清理候选；放宽前先落决策记录（否则下一轮把门加回来，形成震荡）。

## 选择理由

storyboard 换线后的第一次真实运行（项目 61）给了实测：4 场里 2 场需要重试（50%）。两次的原因分属两类：

- `sceneView='rearview'` 不在闭集 `['front','reverse']`——语义唯一，只是词不同，却付出了一整次模型调用。
- 表外角色 `弗兰克` 出现 8 处——真语义错误，重试且回喂候选名单后修好。

第二个数据点来自代码里的既有注释（`pipeline/writer/contract.py`）：只报「不在闭集」时，三次重试全耗在猜简称上；改成把闭集喂回去才解决。这说明重试的效果取决于 reason 的信息量，而不是重试次数。

把这两条合起来看，就有了阶梯：能归一的别重试（省一次调用），需要理解的回喂具体期望（一次能过），只有产物必崩才阻断。

## 被否决的替代方案

| 方案 | 否决原因 |
| --- | --- |
| 违规一律重试 | 词汇差异要付整次调用；实测 50% 的场次因此重试，其中一半是纯同义词 |
| 违规一律归一 | 语义错误无法一一映射（`弗兰克` 不在名单，归一成谁都是错） |
| 先放宽闭集再说 | 放宽会让下游兼容层变厚（见归一边界判据），成本从模型端搬到代码端且不可逆 |

## 影响范围

- 涉及文件/模块：`coding-discipline.md`（新增一小节）
- 兼容性影响：无代码变更
- 后续约束：新增校验时同时声明它属于哪一档；同一项连续成为唯一致败原因时按第 2 条处理
- 未落地（留给项目）：storyboard 的 `sceneView` 别名归一（`rearview`→`reverse`）属产品代码改动，应由派工单处理，主管不写业务代码
