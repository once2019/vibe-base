# 第一性原理进 §3：设计结论要能说出由哪几条约束推出

- 日期：2026-11-15
- 状态：已生效
- 相关模块：`AGENTS.md` §3、`docs/governance/coding-discipline.md`、`skills/vibe-base/README.md` §3

## 决策内容

§3 那条「动手前显式陈述假设」改名为第一性原理，并补一条判据：设计结论要能说出由哪几条具体约束推出，说不出就是照搬惯例或类比。细则层新增「从约束推导，不从惯例推导」一节，把已有的三处第一性原理落点（攻击前提、从头设计、规则来源须是实测失败）归到一处，并划清与「跟随多数用法」的边界。

## 选择理由

- 解决什么问题：这套体系里已经在用第一性原理，但没有名字。`coding-discipline.md` 的「两次失败后攻击前提」是它，「如果一开始就有这个需求会怎么建」是它，`l1-maintenance.md` 的「规则必须来自实测失败模式，禁止从理想实践演绎」也是它。三处各写一遍，遇到第四种情况（技术选型、依赖取舍、流程设计）时无处引用。
- 相比现状的收益：命名后判据统一成一句可判定的问句，答不出具体约束就等于承认理由是惯例。这一条同时解释了为什么本仓三次否决照搬（不引入 uml-viewer、不照搬 ub-mode 的 push 策略、不把质量工具装进项目 `.venv`）：每次都是拿约束顶掉类比。
- 约束条件：§3 只剩 6 行预算，只能改写既有行不能新增行；因此与「陈述假设」合并成一条，判据压到半句，细节放细则。
- 删掉后多久能重建：判据本身能重建（人本能会问为什么），但重建出来的是三处分散的说法，且「说不出约束就是照搬」这句会消失，回退成靠个人发挥。
- 规则来源：`l1-maintenance.md` 要求新规则来自实测失败模式。这里的事实是「方法已在用、未成文、换个人就丢」，证据是既有决策记录里三次约束推导的否决。不是从理想实践演绎出来的新规矩。

## 被否决的替代方案

| 方案 | 否决原因 |
| --- | --- |
| 新建 `docs/governance/first-principles.md` | 现有 `coding-discipline.md` 就是放这类判据的地方，新开文件等于把一份细则按主义拆开；且 init 产出会多一个文件，八份细则变九份 |
| 只写细则，不进 §3 | 细则不保证被加载；技术选型和依赖取舍发生在写代码之前，那时没人去翻细则 |
| 在 §3 单开一行 | 预算只剩 6 行，而这条与「陈述假设」是同一件事的两面（先说假设，再说假设凭什么成立），拆成两行会让读者以为是两条规则 |
| 写成一整套「第一性原理决策法」步骤清单 | 步骤清单会被当成流程执行，而这条要的是问句；且与奥卡姆剃刀、五轴审查产生第三套重叠清单 |

## 影响范围

- 涉及文件/模块：`AGENTS.md` §3 一行改写（行数不变，94 行，单行 116 字符）与 §3 指针行（156 字符）；`coding-discipline.md` 新增一节（86 → 94 行）；`README.md` §3 第一条与 §2 第一层的判据计数（七 → 八）
- 兼容性影响：已初始化过的项目不会自动拿到新 §3，需 `--force` 或人工替换那两行
- 后续约束：判据只有「说出由哪几条约束推出」一句，不再派生检查清单；风格与命名仍按 §3「多种写法并存时跟随多数用法」，不拿第一性原理去推翻既有风格
