# 单技能融合执行编排（vibe-base 内含 foreman 能力）

- 日期：2026-11-13
- 状态：已生效
- 相关模块：`skills/vibe-base/`（SKILL.md、assets/、tests/）、`AGENTS.md`（与 assets 成对）、`docs/governance/orchestration{,-doctrine,-orca}.md`、`docs/governance/dispatch-template.md`

## 决策内容

`vibe-foreman` 不再作为第二个技能存在，整体并入 `skills/vibe-base/`：init 一次同时落治理骨架与执行编排块（`docs/governance/orchestration.md` + `docs/design/` 三份 + `scripts/foreman.py`），能力默认休眠，人类在会话里说「用规划与实施分离把 X 落地」才启用。项目初始化后可删除技能，能力照旧可用。

伴随四项规则重写（不是加一条指针）：

1. §4「AI 生成的代码未经**人类**评审不得合并」→ 评审由人类或主管 Agent 执行，判据是 diff + 改动后验收输出留证；人类评审强制项 = Ask-first 清单全部。
2. §5 记忆归属：`docs/memory/` 由主管独占写入，worker 不写；在跑任务登记于 handoff 运行态节。
3. §3 决策档位统一为「自决 / 主管拍板 / Ask-first」三词，Ask-first 清单是唯一权威。
4. §6 文档体系纳入 `.vibe/`（过程态、不入库、不存在=能力未启用）。

过程态层重新设计：`.foreman/` → `.vibe/`；`task.json.docs.progress` 在 `task new` 时登记落点（不推断）；`report` 直接写 `docs/progress/<日期>-<slug>.md`；Ask-first 裁决必须 `reply --decision-doc` 落 `docs/decisions/`（文件不存在即拒绝），`review` 增 `docs-decisions` 检查项作第二道网。

## 选择理由

- 用户诉求：不想装两个技能；新项目 init 一次，会话里说一句就能派 worker 到独立 worktree、审 diff、合并，主 Agent 不阻塞。并列双技能（原方案 A）不满足「一个技能」。
- 融合而非附加：foreman 的决策档位（T1/T2/T3）、验收前置、审查只信证据与既有 §2/§4 同源，可映射进既有概念（自决/主管拍板/Ask-first），不需要第三套词。
- 状态双源必须消解：`.vibe/` 会消失、`docs/` 入库。定为「审查期认 evidence、归档后认 progress」，并用代码把 Ask-first 决策记录做成硬门槛——否则 §5 决策纪律在并行模式下必然失守。
- 冷启动成本可控：纯标准库单文件，init 从 13 文件增至 18，占位符扫描已排除程序与参考文档（避免 `<taskId>` 类字面量误报为待填项）。
- 预算自校：L1 增 2 行、其余原地并条，实测 93/100 行、最长行 178 字符，不扩预算。

## 被否决的替代方案

| 方案 | 否决原因 |
| --- | --- |
| 并列双技能 + 互引约定（原方案 A） | 不满足「只装一个技能」；两份安装说明、两条路径已实测漂移（codex 只装了 vibe-base、pi 只装了 foreman） |
| init 预建 `.foreman/`（原方案 C） | `.vibe/` 是运行态、不入库，`foreman.py init` 已幂等负责；进模板等于双写，且违反「不说就不启用」 |
| 保留「必须人类评审才能合并」原文 | 与用户「不阻塞主 Agent」直接冲突；折中方案（每次合并都 require_human_review）会让人类回到全程盯 |
| 扩 L1 预算到 110 行 | 为塞内容扩治理约束等于自我豁免；实测 93 行有余量 |
| 协议头 `[FOREMAN:*]` 一并改名 | 属跨进程线格式，改动波及 HEADER_RE、双 transport、1042 行测试；统一措辞收益低于风险 |
| 任务 id 改 `YYYY-MM-DD-<slug>` | 命令行输入长、多次 dispatch 时文件名会漂；改用 `task.json.docs.progress` 显式登记落点，满足 §3 不推断 |
| 控制面脚本按需复制进项目 | 每次要现场判断「这次装哪了」，正是用户要消掉的东西；路径必须确定 |

## 影响范围

- 涉及文件/模块：`skills/vibe-base/{SKILL.md,README.md,assets/**}`、`tests/`（仓库根，回归用，不随技能分发）、`AGENTS.md`、`docs/governance/`（编排四份）、`docs/design/README.md`（撤 3 行索引）、`scripts/foreman.py`（根=assets 镜像）
- 兼容性影响：旧项目 `.foreman/` 不自动迁移，`init` 检出旧目录即 fail-visible 提示 `mv .foreman .vibe`；Orca/hcom 双 transport 行为不变（仍自动判定）
- 后续约束：编排块的条文正本是项目内 `docs/governance/orchestration.md`；改状态机或协议须同步 `docs/governance/dispatch-template.md` 与测试；不得在 `docs/` 下另建第二份编排说明（§6 权威文档唯一）

### 追记 2026-11-13（hcom 名字撞线）

同机两个仓同时派工，两个主管抢同一个 `foreman_name`：worker 的 `[FOREMAN:DONE] task=T-001` 会被另一个仓取走，而两个仓的任务号都从 `T-001` 起。改法：默认名带仓库目录名（`<dir>-foreman`），`doctor` 增 `hcom-name`（同名实例是否挂在别的目录）与 `hcom-address`（会话实际名与配置是否一致）两条检查；Orca 通道按 run_id 寻址，不受影响。条文见 `orchestration.md`「同机多仓并行」。
