# 奥卡姆剃刀作为 §3 的命名原则

- 日期：2026-11-15
- 状态：已生效
- 相关模块：`AGENTS.md` §3、`skills/vibe-base/README.md` §3、`docs/governance/decision-writing.md`、`docs/governance/memory-writing.md`

## 决策内容

把 §3 的「只写解决问题的最小代码」改名为奥卡姆剃刀，适用范围从「修法之间怎么挑」扩到「任何新增先证明删不掉」：新增概念、参数、分支、文件、规则之前，先答「删掉它会发生什么」，答不出具体损失就不加。

## 选择理由

- 解决什么问题：同一条判据此前分散在三个对象上，各自一句话。代码层是 §3 的修法优先序，规则层是 §1 的「删掉它 Agent 会犯错吗」，文档层是 §6 的「权威文档唯一」。三层各自成立，但没有一个共同的问句，遇到新对象（新参数、新文件、新机制）时无处引用。
- 相比现状的收益：命名之后，任何一个「要不要加」的问题都有同一个答法，且答法可判定（答不出具体损失 = 不加）。这条也覆盖人类反复提出的失效模式：新需求进来不查相似实现，每出现一个应用点就加一份，项目随应用点数变臃肿。
- 约束条件：§3 只剩 6 行预算，只能占一行，因此不写判据细节，判据由「答不出具体损失」承担；代价必须写进同一行（l1-maintenance 的 tradeoff 铁律），否则会被当成零成本规则。
- 删掉后多久能重建：随时可重建，但重建出来的是三句分散的话，又回到没名字的状态。可逆，但重建成本高于保留。

## 被否决的替代方案

| 方案 | 否决原因 |
| --- | --- |
| 在 `coding-discipline.md` 新开一节写奥卡姆剃刀 | 与「只写解决问题的最小代码」是同一个概念，新开一节等于把一条规则拆成两处；且细则不保证被加载，红线层才是每次会话自动生效的那层 |
| 只改 README，不动 AGENTS.md | README 是给选型的人读的，项目里的 agent 不读它；规则不落到 §3 就不会被执行 |
| 在派工单里加一节要求 worker 回答「删掉会发生什么」 | 五轴自审的可读性轴已经在问「有没有为以后可能用加的抽象」，再加一节是同一件事写两遍 |
| 同时给 `task new` 加 `--rationale` 参数收这句回答 | 加参数要先答为什么不能删；这里删得掉，DONE 正文写结论即可 |

## 影响范围

- 涉及文件/模块：`AGENTS.md` §3 一行改写（行数不变，94 行）；`README.md` §3 新增一条原则说明；`SKILL.md` 安装与 Tradeoff 两处删掉被 README 覆盖的散文；`decision-writing.md` 与 `memory-writing.md` 各删掉一段对 §3 的原话复述
- 兼容性影响：已初始化过的项目不会自动拿到新 §3，需 `--force` 或人工替换那一行；其余为技能包自身文档
- 后续约束：判据只有一条「答不出具体损失就不加」，不派生出第二套清单；新增规则前仍按 `l1-maintenance.md` 的收录铁律逐行过一遍
