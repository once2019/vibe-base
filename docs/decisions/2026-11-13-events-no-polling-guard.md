# events 不再允许连环开窗口：空等计数 + 通道待收探测

- 日期：2026-11-13
- 状态：已生效
- 相关模块：`scripts/foreman.py`（`MAX_EMPTY_WAITS` / `read_wait_streak` / `Transport.has_pending` / `cmd_events`）、`docs/governance/orchestration.md`（一次闭环）、`docs/governance/orchestration-orca.md`

## 决策内容

1. **一次 `events` 调用 = 一轮**。连续两轮空等（`MAX_EMPTY_WAITS=2`）后，第三次调用直接 `fail`，不再进入阻塞等待；错误输出写明「结束回合、在 `handoff.md` 运行态写一行在等什么」。
2. 空等超时的输出从「等待超时，无匹配协议消息」改成带下一步动作：第 N/2 轮、结束回合、写 handoff。
3. 计数存在 `.vibe/logs/events-waits.json`，**消费到任何一条协议消息即清零**；超过 30 分钟（`WAIT_STREAK_TTL_MIN`）也视为不连续，重新计数——上个会话留下的计数不该拦住这个会话的第一次等待。
4. 新增 `Transport.has_pending()`：Orca 用 `check --peek`（只读不标记），hcom 用 `list --json` 的 `unread_count`，探测不了返回 `None`。**达到上限时若确有消息在等，放行消费**，避免把主管锁在门外。
5. `orchestration.md` 的一次闭环拆成「回合一：派工」「回合二：被唤醒后」，明确 `events` 是第二个回合的入口，不是派工之后的下一步。

## 选择理由

- 实测事故：主管把 `events` 当轮询，连着开了 420s / 540s / 540s 三个窗口空转，同一时间本该结束回合等唤醒。
- 根因是条文歧义 + 没有拦截。旧文写「同一 dispatch 最多两轮」，没说「轮」是一次调用还是一次派工，也没说为什么是两轮；`events` 又恰好排在派工之后的下一行，读起来就是「派完接着跑它」。
- 这条规则此前不可判定（`l1-maintenance.md` 的可判定性铁律）：没有任何东西能在主管第三次开窗口时说话。改成按调用计数并由代码拦截后，它变成可判定动作。
- 为什么放行「有消息在等」：拦截的目的是不让人空转，不是不让人收信。若一到上限就一律拒绝，主管被唤醒后反而收不了消息，只能手工改状态文件，那是更坏的结果。

## 被否决的替代方案

| 方案 | 否决原因 |
| --- | --- |
| 只改文档措辞，不加拦截 | 同一类错误在 hcom 时代已经出现过一次（旧技能「`--wait` 死等」条目），说明只写不拦不够 |
| 按 dispatch 记账（每个 dispatch 两轮） | `events` 不区分 dispatch，要记账就得给命令加 `--task`，把简单命令变复杂；连续空等本来就是要结束回合的信号 |
| 到上限一律拒绝（不探测待收） | 会把主管锁在门外：被唤醒后第一条命令就是 `events`，拒了就没法消费 |
| 给 `events` 加 `--force` 逃生门 | 逃生门会被当成默认路径；真要等就结束回合，唤醒机制本来就会叫 |
| 上限做成 config 键 | 多一个概念却没有第二组合理取值；常量 + 决策记录足够 |

## 影响范围

- 涉及文件/模块：`skills/vibe-base/assets/scripts/foreman.py`（`has_pending` 接口 + 空等计数 + 提示文案）、`orchestration.md` / `orchestration-orca.md`（回合边界与「轮」的定义）
- 兼容性影响：`events` 在连续两次空等后第三次会非零退出（此前会继续阻塞）。正常用法（派工 → 结束回合 → 被唤醒 → events）不受影响，因为唤醒时必有消息，计数在消费后清零
- 实测：测试 134 → 141；九处守卫变异全部转红（上限拦截、待收放行、空等计数、消费清零、结束回合提示、保鲜期、探测不了放行、拒绝文案、Orca peek）
