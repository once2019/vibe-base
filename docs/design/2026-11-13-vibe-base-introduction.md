## 一、vibe coding 的通用问题

让 agent 干活，遇到的麻烦大多不在"它不会写代码"，而在协作的基本条件缺失：任务边界、判据、记忆、审查、并行、成本。下面这些是编码工作本身长出来的问题，与用哪套工具无关。

单个会话干不了大任务。上下文是有限的，而且会随着改动累积被挤占。一个任务从读代码、定方案、改五六个文件到跑通测试，做到后半段时前半段定下的约定已经在窗口边缘了。agent 开始忘记最初的约束，改出来的东西与开头说的目标有偏差，而且它自己察觉不到。

自己审自己等于没人审。同一个会话写代码又做验收，会系统性地漏掉自己写错的假设。它挑的测试用例覆盖的是它想到的路径，它读 diff 时看到的是自己的意图而不是文件内容。让人审，人又不可能每分钟都在。

"做完了"没有判据。agent 说"测试通过"，可能是三小时前的输出，可能是它新写的一个只覆盖顺利路径的测试，也可能它把失败的用例删了。人得重新跑一遍才能确认，而这遍验证的成本往往比写代码本身高。

顺序依赖的活只能串着做，人得全程在。有些任务天然有先后：改完接口才能改调用方，改完调用方才能补回归。串着做的时候，每一步之间人要等 agent 报告、判断、再下一条指令。等的时间比干活长。

多个会话同时改一个项目，改动互相踩。两个会话可能都在动同一个文件，各自在自己的分支上很顺，合并时冲突；更麻烦的是不冲突但语义打架，一个删掉的字段另一个还在读。没有隔离的话更糟，直接改同一个工作区，谁的改动覆盖谁全看运气。改完不推的人还会攒出一堆分叉。

同一项目的并行会话互相看不见对方在干什么。A 会话在重写渲染管线，B 会话不知道，照着旧接口写调用方，等两边合起来才发现对不上。两个会话也可能各自领了同一件事，做两遍。共享的记忆文件同样会打架：`context.md` 和 `handoff.md` 两个会话都要写，后写的把先写的覆盖掉，或者各自记了一份互相矛盾的状态，新会话读到哪份取决于谁最后保存。

主、子 Agent 模式下，子 agent 停住了主 agent 不知道。普通 vibe coding 里很常见的分工：主 agent 把一部分活交给子 agent 去另一个终端跑，自己在原地等结果。子 agent 遇到拿不准的地方可能猜着往下做，也可能停下来等指令。停下来的时候，它那边没有任何信号传回主 agent，主 agent 以为它还在干活。这个模式缺的就是回传路径：分不清对方是在思考、在等，还是已经退出。

记忆不跨会话。第二天开新会话，它不知道昨天做到哪、试过什么、为什么放弃方案 A。于是重新读代码、重新调研，有时把已经失败过的路再走一遍。人的补救办法是写一份进度说明塞进 prompt，越塞越长，最后自己也不维护了。

规则文件既膨胀又自我矛盾。起初只想写"别删测试"，三个月后 AGENTS.md 四百多行，混着构建命令、目录说明、编码风格、临时 workaround。agent 每个会话读一遍，token 花在读规则上。更麻烦的是开始互相矛盾：一处说测试必须全绿，另一处说赶时间可以先合。agent 挑对自己有利的那条执行，没人知道现行版本是哪条。

决策理由蒸发。三个月后有人问"为什么不用 X"，代码里没有答案，聊天记录翻不到，只好再评估一遍，可能得出相反结论，也可能重复踩同一个坑。

危险动作没人把门。引入依赖、删数据、改 CI，agent 有时自己就做了，做完才在报告里提一句。哪些动作必须先问人，这件事没有集中清单的话，每个会话的理解都不一样。

强模型的时间花在杂活上。改文案、批量重命名、补测试这类活，能力强弱的差别不大，但占用的都是同一条会话、同一份注意力。全部交给一个模型做，贵的部分被浪费，便宜的部分也没省下。

文档与代码各自演化。代码改了文档没动，文档改了代码没跟上。半年后没人知道哪份是现行。

多人多 agent 交替接手，口径开始漂移。同一个概念在三处叫三个名字，"进行中"有两种说法，"已完成"的判据也不一致。新接手的人得先花半天对齐术语，才看得懂状态。

## 二、vibe-base 设计的机制如何解决

vibe-base 装进项目的是两层东西，启用条件不同。

第一层是编程规范与管理。协作红线、三层记忆机制、决策记录、文档体系管理、Ask-first 规则都写进 `AGENTS.md`，配一个体检脚本；`init` 之后每个会话都加载，不派工也在生效。它管的是"一个会话怎么把活干得可追溯、可交接"。

第二层是主管 / worker 执行编排。会话里说一句"用规划与实施分离、用 worker 模式处理 X"或任何近似表达，当前会话立即变身主管 Agent，把任务拆出去、隔离实施、异步收结果。它管的是"多个 agent 怎么分工而不互相破坏"。

两层的组织方式一样：常驻层只放红线和目录，细则层放"怎么做"的操作条文。`AGENTS.md` 里是一行指针加行为红线，命令序列、决策档位、审查判据这些细则落在项目自己的 `docs/governance/` 下。这样常驻部分能压到一百行以内，每次会话自动生效，不必赌"技能会不会被想起来"，也不依赖技能还装着。

两层管的是不同的事，有几处必须配合。下面按层来讲。

### 第一层：编程规范与管理

这一层的载体是仓库里的文件，不需要任何通道或派工动作。

#### 三层记忆：不同寿命的信息分开放

L1 是仓库根的 `AGENTS.md`，常驻上下文，只放目录和红线。L2 是 `docs/decisions/`，每条决策带理由与被否决方案，配一份索引。L3 是 `docs/memory/`：`context.md` 是项目状态快照，`handoff.md` 是给下一个会话的交接包。

会话开始时读 context、handoff 和决策索引最近三条；收尾必须写 handoff，无例外。快照只记当前状态，完成项移交 `docs/progress/` 后立刻从快照删掉，留着就退化成流水账。

并行会话的写入纪律单独规定：先读最新版，做精确片段替换，禁止整文件覆盖，禁止原地追加。`docs/memory/` 由主管独占写入，派工实施的 worker 不写，它的结论走 DONE 正文，由主管合并后统一落盘。这条挡住的正是"两个会话各写一份互相矛盾的状态"。

#### 规则受预算约束

`AGENTS.md` 不超过 100 行且单行不超过 200 字符，context 不超过 40 行、单行 150 字符，handoff 不超过 60 行、单行 150 字符。`doctor` 的 `governance-budget` 实测行数和最长行字符数，超了直接 FAIL。

只有预算还不够，还得有收录标准。三条铁律决定一条规则能不能进：删掉它 agent 会犯错吗（不会就删）；能不能被 lint、测试或评审验证（"注意代码质量"不行）；有没有实测失败模式作为来源（从理想实践演绎出来的不收）。另加一条 tradeoff 铁律，行为条款必须声明代价和豁免域。`AGENTS.md` 是唯一事实来源，其他文档只作出处引用，不复述，写新规则前先全仓搜一遍。规则改动的顺序不可反：先落决策记录，再改规则文件。

#### 决策记录：把理由留在代码旁边

建条判据是"下个会话看了代码会问为什么不用 X"。每份记录四节：决策内容一句话，选择理由覆盖四问（解决了什么问题、相比现状收益、受什么约束、删掉后多久内可重建），被否决的替代方案必须具体到技术事实（写"不好""不优雅"不算），影响范围含后续约束（写"注意性能"不算）。

建条即登记索引，一行一条。`doctor` 的 `decisions-index` 双向核对：文件存在但索引没有（孤儿）、索引指向不存在的文件（死链），任一出现即 FAIL。术语唯一性也管在这里，新机制引入时定一个名字，全库沿用，改名属于方向性变更，要走决策记录。

#### 危险动作集中一处

Ask-first 清单只在 `AGENTS.md` §4 维护：引入第三方依赖、安装系统级依赖、改 CI/部署配置、删数据、force push，加项目特定条目。其他文档只作出处引用，不复制清单。每个会话加载同一份清单，理解就不会各自发挥。

#### 文档与代码同一次提交

`docs/` 全部入库，与代码同一次提交，不允许"代码已改、文档没动"进主干。需求变更先改 `docs/specs/` 的描述与验收标准，再改代码。新建权威文档前先查所在目录的 README 索引，未命中可直接建，建完立刻登记一行。

落到文件上是六处：`AGENTS.md` 放红线和目录，`docs/decisions/` 一条决策一个文件，`docs/memory/` 放状态快照与跨会话交接，`docs/progress/` 放进度与竣工单，`docs/specs/` 放需求规格，`docs/design/` 放设计文档与调研分析。

### 第二层：主管 / worker 执行编排

先说分工。主管是人类直接对话的那个会话，负责拆分、裁决、审查、合并。worker 是主管拉起的子 agent，只负责实现和上报。两者之间用消息通道通信，状态落在仓库的文件里。

#### 隔离实施：一棵树一个任务

`dispatch` 给每个任务建独立的 git worktree 和分支。worker 的全部改动收敛在自己的分支上，主管拿到的是完整 diff 而不是口头摘要；合并之后删树，主仓库不留运行态垃圾。Orca 通道下由 Orca 托管这棵树，hcom 通道下由 `foreman.py` 自己建在 `.vibe/worktrees/`。

这一条同时挡住两种互相踩：多个 worker 之间，各自在自己的树里，改动不互相覆盖；主仓库这边，主管的工作区始终干净，不会有人在你脚下改文件。任务切小的粒度判据是"一次能审完"，diff 控制在三百行上下；口子是能否独立验收，不是按文件数切。

#### 拆分权留在主管手里

这条有具体理由。拆分产物就是范围与验收，而这两样正是审查的锚点。范围由 worker 自己定，`review` 的 `scope` 检查就恒真；验收由 worker 自己定，`acceptance` 检查也恒真，等于自证清白。`dispatch` 的 scope 相交拦截、`--depends-on` 前置门槛同样依赖主管定的范围与依赖，下放拆分会让这几道门一起失效。

要下放可以走两段式：先派一个只读的拆分任务，验收写成"方案文档存在且列出子项与各自验收命令"；主管审完清单，再用 `task new --item … --accept …` 建实施批次。子项彼此独立、验收口径统一（比如一条全局 `mypy` 覆盖）的时候，可以直接让 worker 分块。

#### 决策权分三档

档位只有三个固定名字，全库沿用。自决是 worker 说了算：实现细节、命名、范围内的小取舍。主管拍板是接口形态、文件归属、测试策略、换路、重派、拆任务、扩 scope 这类。Ask-first 是 `AGENTS.md` §4 那份清单，必须人类点头。

前两档在过程态里留痕，第三档还要落一份决策记录。把主管拍板的事抬成 Ask-first，人类回到全程盯，模式失去意义；把 Ask-first 压成主管拍板，不可逆的错误没人拦。拿不准就抬到 Ask-first，成本只是等一次。

#### 完成定义先于实现

`task new` 时两条硬判据：`--scope` 必须列路径，禁写"相关文件"；`--accept` 必须是一条可执行命令，禁写"确保测试通过"。写不出验收命令说明需求还没想清，这时候派工只会得到一份看起来像完工的报告。

`review` 跑六项检查：`scope`（越界）、`secrets`（密钥）、`no-skip`（跳测试或 `--no-verify` 痕迹）、`non-empty`（空改动）、`acceptance`（复跑验收）、`docs-decisions`（决策记录是否齐）。前五项机械判定，第六项是治理门槛。复跑的输出存进 `evidence/`，`merge` 之后在主干上再跑一次。竣工单写"验证方式"节，含可复现命令、关键输出、覆盖数 n/N。审查期只认 `evidence/`，归档后只认 `docs/progress/`，分两段是因为过程态要能删（`.vibe/` 不入库），结论要留（入库）。

#### 异步回合：被唤醒而不是守着

一次派工跨两个回合。回合一做 `doctor`、`task new`、`dispatch`，做完就结束回合，不 sleep、不开等待窗口。worker 需要请示或完成时发消息，通道把主管叫醒，进入回合二跑 `events`。

回合的概念要写清楚：一次 `events` 调用算一轮，连续两轮空等后第三次调用直接拒绝，输出指向结束回合。主管的空闲时间不被耗在等待上，多个任务同时在跑时只在有事件时消耗注意力。

#### 请示与上报是一套固定协议

主、子 Agent 模式缺的是回传路径，这一节补的就是它。worker 只能发三种消息，写进 `subject` 的第一行：`[FOREMAN:ASK]`、`[FOREMAN:DONE]`、`[FOREMAN:ESCALATE]`。拿不准就问（附问题、选项、推荐项），不许猜；完成就上报（附摘要、改动文件、自审结论、验证输出、提交）；卡住就升级。

DONE 之前必须先自审三样：机械四项（改动面是否都在范围内、验收命令是否真实跑过、有没有跳过测试、有没有密钥）、五轴过一遍自己的 diff（正确性、可读性、架构、安全、性能）、反证一次（取反新增的一个条件，确认对应测试转红再还原）。结论写进 DONE 正文并逐条标严重度，主管按同样口径复核，不采信自报。

依靠 worker 守规矩之外，还有不依赖它守规矩的手段：`worker-read --source terminal` 直接读它的终端输出，看它停在哪一步。

#### 并行与批次的机械判据

能不能并行由代码判定，不靠主管记性。`dispatch` 比对所有在跑任务的 scope，与本任务相交就拒绝，并列出相交的那一对路径；确实要在同一处并行（各改一个不相邻的函数），加 `--allow-overlap` 显式承担合并风险。

有顺序依赖的一串子项不拆成多次派工，而是整批派给一个 worker：同一棵树里逐项做，每项一个 commit，每项一份验收证据，主管只在整批结束时审一次。逐个派工意味着每个子项一轮 `review` 加 `merge`，而且这条链本来就跑不成并行。

`task new --depends-on T-001` 让前置未 `completed` 的任务无法派工，报出前置当前状态。它只做门槛，不建 DAG、不自动触发后续任务。

#### 谁能干谁干

`task new --agent` 或 `dispatch --agent` 指定 worker 用哪个 agent，不指定就跟随主管会话。选法按要读多少上下文分：跨模块、要读多处既有实现、要判断设计取舍的，给能力强的；机械替换、改文案、补测试，给便宜快的。

#### 失败之后怎么走

同一个任务最多派三次。前两次算任务可修，修完重新派工，worker 在同一棵树上接着改，主管看到的是累计 diff；第三次进 `blocked` 交人，不再自动重派。重派必须写 `--retry-note` 说明这次改了什么，不带就直接拒绝，因为不写说明的重派等于让它重跑一遍同样的错误。

三次用完仍失败，该问的是任务是不是拆大了，而不是再派一次会不会好。合并之后另说：复跑验收不过就停在 `merge_ready`，由人决定回退还是修复，不自动重试。

### 两层合起来才成立的几处

单靠任何一层都接不住，下面三处是配合的结果。

完成判据：编排层提供可执行命令与证据文件，治理层提供审查口径（六项机械检查加五轴读 diff）和"反证一次"的要求。只有命令没有审查口径，会合并一份测试全绿但结构更糟的改动；只有口径没有命令，等于凭感觉。

并行：编排层给隔离树、scope 相交拦截和前置门槛，治理层给记忆写入归属和术语唯一。少了前者，改动互相踩；少了后者，代码不冲突但文档和状态各记一份。

危险动作：编排层给 `ASK` 协议和阻塞门（任务转 `waiting_human`，主管把问题转述给人类），治理层给清单本身和 `reply --decision-doc` 硬闸（Ask-first 裁决必须同时落决策记录，文件不存在直接拒绝），`review` 的 `docs-decisions` 是第二道网。三层缺一层，绕过就成立。

## 三、原理与取舍

### 三套理念来源

规则不是凭空长出来的，主体来自 Karpathy 的三套公开写作，各管一层。

Guidelines 管 Agent 写代码的常见病：动手前把假设说清楚、只写解决问题的最小代码、外科手术式修改、先定义怎么算完成。落到 `AGENTS.md` 就是 §3 那几条。

LLM Wiki 管知识怎么积累。多数人用 LLM 处理文档是问一次查一次，什么也不留；另一种做法是让它把知识编译进一个持续维护的维基，新资料进来就消化，查询得到的分析也回填。落到项目里，调研结论、方案比较、根因分析写进 `docs/design/`，被否决的替代方案写进 `docs/decisions/`，下次碰到同类问题直接查。它成立的前提只有一条：知识库的常见死因是没人维护，而维护恰好是 LLM 不嫌烦的部分。

受控文字管沟通。空客的维修手册用 ASD-STE100 受控英语，句长有上限，一个动词只许一个意思。落到协作里，同一个概念只许一个名字，一句话只说一件事，"尽快处理"必须换成具体日期。

三套背后还有共同的元设计：规则必须来自实测的失败模式，不能从理想实践往下推；每条规则配一个能自查的问句（"这行改动是用户要的吗"）；每条规范要承认自己的代价。这三条决定了规则怎么写、怎么被推翻。

### 可判定优先

一条规则能不能被机器或评审检验，决定它算不算规则。"注意代码质量"不是规则；"提交前 ruff、mypy、pytest 全部通过且贴出本次输出"是规则。两层机制里几乎每条都有对应的检查：`doctor` 十七项，`review` 六项，`dispatch` 三道门。

代价是有些本该模糊的判断被压成了机械判据，偶尔会误报。处理办法是给误报留显式出口（`--allow-overlap`），而不是放宽判据。

### 状态与事件分离

`task.json` 是唯一事实源，通道消息只是事件。这是从分布式系统搬过来的老道理：消息会丢、会重复、会被旁路消费，状态必须有唯一落点且写入幂等。任务是十一个状态的显式迁移表（`pending` 到 `completed`，加 `failed` 与 `blocked`），非法迁移直接拒绝。

### 机制自己也会坏，所以要自己的护栏

上面那些机制都依赖外部系统：消息通道、git、Orca。它们会失效，失效时的表现往往是"任务悄无声息地停住"。所以机制本身也带着几条护栏。

`foreman.py reconcile` 拿通道的权威事实对三条账：dispatch 状态（通道说完成而状态机还在跑，说明 DONE 没进状态机）、liveness（worker 已退出但没上报）、消息落地（消息被读走却没有对应证据）。`doctor` 每次体检跑一次。

合并后的清理先落盘状态再执行，清理函数绝不抛异常，每步结果写进 `task["cleanup"]`，`doctor` 的 `resource-leaks` 报残留。`git worktree remove` 失败后会 prune 重试一次。多仓同时使用时 `foreman_name` 带路径哈希后缀，`doctor` 检查名字有没有被别的目录占用。

这些护栏只管机制自身的可靠性，上面列的工程问题不靠它们解决。

### 失败可见，不取默认值

缺字段就报错，不猜。`reconcile` 认不出是哪个任务时先留档再失败，不静默跳过；`reply` 缺决策记录直接拒绝；`dispatch` 的前置门槛报出前置当前状态而不是"大概没完成"。

### 门与调度分离

`--depends-on` 只回答"能不能派"，不回答"什么时候派"。省掉调度器，也省掉调度器带来的时序 bug。

### 默认休眠

能力常备但不动。`init` 只建空的 `.vibe/` 骨架和忽略规则，不装通道、不探测、不派工。日常会话零开销，人类说一句"用规划与实施分离把 X 落地"才启用。目录存在不等于启用，判断看有没有在跑的任务。

### 治理能自我修正

规则会过时，也会被反复违反。体系留了一条修正通道：决策数到 20 条时，`doctor` 的 `governance-budget` 提示跑一次复盘，正本是项目里的 `docs/governance/governance-review.md`，带 8 个自查问句和再复盘的信号清单。

信号里有几条机械可查：任一记忆文件超双预算、决策索引超过一屏还没建或停止维护、同一主题的决策被追记超过 3 次、同一条规则在两处出现且表述开始分叉。知识健康另有三查：文档之间的矛盾陈述、被推翻的决策仍被引用、无入链且长期没更新的孤儿文档。复盘产出固定为「问题 → 证据 → 改法」表格，没有证据的体感不入清单。

这条通道的意义在于：发现规则被反复违反时，先修规则再按新规则执行，不允许"下不为例"。

整套体系偏向正确而不是速度。证据门槛会否决一部分"感觉对"的改进，细则加载和自查会拖慢写作节奏，常驻部分占用不到一百行上下文。琐碎任务凭判断简化，不必全套走一遍。

### 取舍清单

| 选择 | 换来 | 代价 |
| --- | --- | --- |
| 占位符 `<...>` 回填制 | 冷启动不追问用户 | 骨架长期留占位符，回填靠后续会话自觉 |
| `foreman.py` 单文件约 2900 行不拆 | 复制即用、零依赖、单处审计 | 文件大，改动要在段落间跳 |
| 编排能力随骨架发（16 个文件） | 一个技能、一次安装 | 新项目多一个可能不用的脚本 |
| 项目自持副本 | init 后删掉技能照旧可用 | 不随技能升级，需 `--force` 或人工对照 |
| 根目录与 assets 用符号链接镜像 | 一份实体，零漂移 | Windows 检出要 `core.symlinks=true` |
| 批次任务（一串子项一个任务） | 只审一次，省往返 | diff 更长，第 3 项失败整批回退 |
| 默认主管拆任务 | 审查锚点成立 | 主管带宽成为瓶颈 |
| `events` 不设 `--force` 逃生门 | 规则不会被绕过成默认路径 | 探测失败时可能多等一轮 |
| 合并后不自动 push | 人保留最后决定权 | 每次要手动推 |
| 记账用 JSON 文件 | 无依赖、可直接读、可 grep | 没有并发保护，靠"主管唯一"这条前提 |

## 四、什么时候用，什么时候别用

适合这几种情况：

项目有可执行的验收命令（测试、lint、构建能跑起来）。任务能拆成"一次能审完"的粒度，diff 在三百行上下。需要多任务并行且互相隔离。项目要长期维护，决策得能追溯。会有多个 Agent 或多人交替接手同一个仓库。存在不可逆动作需要人把关，比如删数据、引入依赖、改部署。

不适合的：

改一行文案、改个变量名。派活的开销是收益的十倍。需求还在模糊期，先用提问把目标问清楚，否则派出去的是猜。需要人在旁边频繁做审美或口味判断，阻塞门会占满人类带宽，绕一圈还是全程在场。跨仓库或跨服务的改动，一棵树装不下，先拆成两个需求。一次性脚本和 demo。没有测试基础设施的项目，验收命令写不出来，整套审查就失去锚点。

## 五、最小起步

初始化由一个技能触发：新项目里说一句「初始化项目治理」或「init AGENTS」。产出是 16 个文件（1 份 `AGENTS.md`、14 份 docs、1 个控制面脚本 `scripts/foreman.py`），外加空的 `.vibe/` 骨架和写进 `.git/info/exclude` 的忽略规则。幂等，不覆盖已有文件；占位符不追问，agent 在后续开发中获知实际信息后自己回填。初始化之后技能就可以删掉，能力由项目自持。

`init` 之后先做三件事，别一上来全用：

一是把 `AGENTS.md` 里 Agent 猜不到的占位符填掉，尤其是测试、lint、类型检查三条命令。二是给第一个任务写一条真能跑的验收命令。三是跑一次 `doctor`，红了先修红项再派工。

三层记忆和决策库是随开发自然长起来的，不用开局就写满。编排能力在第一次真的要并行时再启用。
