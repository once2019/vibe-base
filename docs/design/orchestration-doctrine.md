# 执行编排理念 — 主管 / worker

- 变更日期：2026-11-13
- 变更原因：并入 vibe-base 治理体系——操作面统一指向 `docs/governance/orchestration.md`，过程态目录改为 `.vibe/`
- 关联：`docs/governance/orchestration.md`（操作面与落点分工）、`docs/design/dispatch-template.md`（派工单写法）

## 为什么是这三层

主管的价值不在写代码，而在**拆解、裁决、验证**。要让"验证"可信，必须满足：

1. **隔离**（git worktree）：worker 的全部改动收敛在自己的分支上，主管拿到的是完整 diff 而不是口头摘要；合并后删树即清理，仓库不留运行态垃圾。hcom 模式下 foreman 自建 `.vibe/worktrees/`，Orca 模式用 Orca 托管 worktree。
2. **事件**（hcom 或 Orca 编排）：worker 请示/上报时主管会话可能正闲着——只有消息能唤醒它。文件轮询做不到，所以消息通道必须是能唤醒 agent 的编排层（hcom 或 Orca `orchestration`），不能用临时文件传消息。
3. **状态**（`.vibe/` 文件）：消息流不适合当事实源（难查全貌、无幂等）。任务状态、派工记录、证据全部落 `task.json` 与 `evidence/`，任何会话随时可恢复上下文。

三层各司其职，越界即错：拿消息当状态、拿文件当消息、在主仓库直接改 worker 分支，都是红线。

## 完成定义先于实现

`dispatch` 之前必须存在验收命令。没有可执行判据的任务不允许派工——"能跑"不是完成，"验收命令在改动之后真实跑过且通过"才是。派工单里写清三件事：目标、范围（允许改动的路径）、完成定义。范围能窄则窄；范围含糊的 worker 必然越界。

## 审查只信证据

`review` 的六项判据中四项可自动化（范围、密钥、跳测痕迹、验收通过），两项必须人工判断（提交质量、决策/文档同步）。自动检查全绿 ≠ 符合意图：主管仍需读 diff 本身，确认改动集合与提交叙事讲得通。证据（diffstat、验收输出、协议消息全文）随任务存档，竣工单里每个数字都要能指到 evidence 文件。

## 失败是重派，不是重试

第 N 次 dispatch 复用同一棵 worktree——worker 在原分支上继续修，主管看到的是累计 diff。三次失败的语义不同：第 1、2 次失败说明任务可修；第 3 次进 `blocked`，说明问题在拆解或定义层面，继续自动重派只是烧 token。blocked 只能由人类解锁。

## 何时立 T3 门

主管拿不准 = 人类该拍板。宁可多立一次 `ask`（任务挂起，零成本）也不要替人类做 T3 决策——架构改动、schema、依赖、CI、删数据、测试不绿要合并，这些一旦做错回退成本远高于一次等待。立门后主管把问题与选项转述给人类；`reply` 即落实裁决并记录在案。

## 主管的时间片

主管每轮只做一步（拆任务 / 派工 / 答复 / 审查 / 合并），然后结束回合。编排通道负责唤醒，主管不轮询、不 sleep。这是事件驱动模式的全部意义：多个任务并行时，主管只在有事件时消耗注意力（等待次数上限属操作细节，见 `docs/governance/orchestration.md` 主管循环）。

## 什么时候不该用这套

- 改一个变量、改一行文案：直接做，派活开销是收益的十倍。
- 需求还在模糊期：先用 interview 问清目标，否则派出去的是“猜”。
- 需要人在旁边频繁做美学/口味判断：T3 会占满人类带宽，绕一圈还是要全程在场。
- 跨仓库/跨服务的改动：一棵树装不下，先拆成两个需求。

## 决策档位的两种误用

把 T2 抬成 T3（什么都问人类）→ 人类回到“全程盯”，模式失去意义；把 T3 压成 T2（自己批架构/依赖/删数据）→ 不可逆错误没人拦。拿不准就抬到 T3，成本只是等一次。
