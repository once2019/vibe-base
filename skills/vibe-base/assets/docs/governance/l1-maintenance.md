# L1 维护细则（AGENTS.md 与模板规则）

> 本文件管"规则怎么改才合规"。复盘流程见 `governance-review.md`。

## 收录铁律判定（写入前逐行过）

- 每一行问："删掉它，Agent 会犯错吗？"——不会，就删。
- Agent 读代码、构建文件、`--help` 即可获知的信息不入 L1；参数级细节给指针不展开。
- 可判定性：每条规则必须能被 lint、测试或评审验证；「注意代码质量」这类不可执行表述禁止出现。
- 规则来源铁律：新规则必须来自实测失败模式（问题→证据），禁止从理想实践演绎；无运行痕迹证据的规则不入规范。
- self-check 铁律：每条行为规则附一个可自查问句或可机械执行的验证方式（例："每一行变更都能追溯到当前请求吗？"）。
- tradeoff 铁律：代价与豁免域记于决策记录，L1 只写规则本体与适用边界；边界须有真实误执行证据才写。
- 规范不带论据：细则写做法与判据，不写原因、推导与历史过程；论据归 `docs/decisions/`，例子只作判据示例出现。代码注释与决策记录不受此限。
- 术语唯一性：新规则引入新概念时须定义唯一名称，全库（规则、决策、设计文档、记忆）一律沿用；改名属方向性变更，须走决策记录。
- 双预算：≤100 行且总 ≤10000 字符（不设单行上限）；逼近预算时先修剪内容，不压缩措辞。

## 写入前查重

- 新规则先搜全仓（AGENTS.md、docs/）确认无第二份表述；他处已有的只作出处引用，不复制。
- 新规则写入唯一对应章节：命令类 → §2，风格红线 → §3，安全与 Ask-first → §4，记忆协议 → §5，文档同步 → §6；Ask-first 新事项一律进 §4 集中清单。
- 项目级特例放子目录 AGENTS.md（离被改文件最近的优先），不膨胀根文件。

## 修订流程（单条规则变更）

1. 确认变更性质：小补充 → 决策记录文末追记；方向性推翻 → 另建新决策记录并互相引用，旧条状态行改「已被 <新决策> 取代」（选路判据见 decision-writing 细则）。
2. 先落决策记录，再改规则文件。
3. 修改规则文件：`AGENTS.md` 或 `docs/governance/` 下对应细则；同时刷新 `docs/design/` 相关文档的变更日期与原因标注。
4. 验证：按新规则跑一次相关流程并展示命令与输出；改 L1 后核对双预算（≤100 行且总 ≤10000 字符）。

## 优先级冲突裁决

裁决链：**人类明确指令 > 离被改文件最近的 AGENTS.md > 仓库根 AGENTS.md > 代码现状**。

- 冲突出现时当场裁决并说明依据的链级；裁决结论固化进对应层的规则文件，不留在对话里。
- 相抵的规则对（文本规则 vs 实测衍生规则）按复盘流程调和：终态语义保留，写法取实测可行的那个，明文写入 L1。

## 修剪

- 定期自查："Agent 读代码即可获知"的冗余是 L1 膨胀的主因，发现即删。
- L1 预算（≤100 行且单行 ≤200 字符）超标 = 复盘信号，转 `governance-review.md` 流程处理，不就地硬压。
