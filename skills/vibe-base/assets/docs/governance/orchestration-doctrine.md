# 执行编排理念 — 主管 / worker

- 关联：`docs/governance/orchestration.md`（操作面、派工单判据与落点分工）

## 三层各司其职

| 层 | 载体 | 职责 | 越界即错 |
| --- | --- | --- | --- |
| 隔离 | git worktree | worker 的改动收敛在自己分支上，主管拿到完整 diff；合并后删树 | 在主仓库直接改 worker 分支 |
| 事件 | hcom 或 Orca 编排 | 唤醒主管会话；消息必须是能唤醒 agent 的通道 | 拿文件当消息 |
| 状态 | `.vibe/` 文件 | 任务状态、派工记录、证据落 `task.json` 与 `evidence/`，任何会话可恢复上下文 | 拿消息当状态 |

hcom 模式下 foreman 自建 `.vibe/worktrees/`，Orca 模式用 Orca 托管 worktree。

三层各司其职：拿消息当状态、拿文件当消息、在主仓库直接改 worker 分支，都是红线。

## 完成定义先于实现

`dispatch` 之前必须存在验收命令。没有可执行判据的任务不允许派工。派工单里写清三件事：目标、范围（允许改动的路径）、完成定义。范围能窄则窄；范围含糊的 worker 必然越界。

完成的判据是目标达成 + 已知偏差留痕，验收命令是主要证据而不是全部。遗留项按可直接派单的形态列出来（改哪、验收命令），带遗留交付算正常完成，不算失败；遮挡遗留或把偏差说成通过才算失败。

## 审查只信证据

`review` 的六项判据中四项可自动化（范围、密钥、跳测痕迹、验收通过），两项必须人工判断（提交质量、决策/文档同步）。自动检查全绿 ≠ 符合意图：主管仍需读 diff 本身，确认改动集合与提交叙事讲得通。证据（diffstat、验收输出、协议消息全文）随任务存档，竣工单里每个数字都要能指到 evidence 文件。

## 失败是重派，不是重试

第 N 次 dispatch 复用同一棵 worktree——worker 在原分支上继续修，主管看到的是累计 diff。三次失败的语义不同：第 1、2 次失败说明任务可修；第 3 次进 `blocked`，说明问题在拆解或定义层面，继续自动重派只是烧 token。blocked 只能由人类解锁。

## 何时立 T3 门

不属于自决与主管拍板的事项一律人类拍板（清单见 `AGENTS.md` §4）：架构改动、schema、依赖、CI、删数据、测试不绿要合并。立门后主管把问题与选项转述给人类；`reply` 即落实裁决并记录在案。

## 主管的时间片

主管每轮只做一步（拆任务 / 派工 / 答复 / 审查 / 合并），然后结束回合。编排通道负责唤醒，主管不轮询、不 sleep（等待次数上限见 `docs/governance/orchestration.md`）。

## 什么时候不该用这套

- 改一个变量、改一行文案：直接做。
- 需求还在模糊期：先问清目标再派。
- 需要人在旁边频繁做美学/口味判断：直接做。
- 跨仓库/跨服务的改动：先拆成两个需求。

## 决策档位的两种误用

把 T2 抬成 T3（什么都问人类）会让人类回到全程盯；把 T3 压成 T2（自己批架构/依赖/删数据）会让不可逆错误没人拦。档位按 `AGENTS.md` §4 清单定，不按感觉定。
