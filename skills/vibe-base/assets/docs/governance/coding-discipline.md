# 编码纪律（§3 的操作条文）

> §3 是红线，本文件是操作条文；冲突以 `AGENTS.md` 为准。
> 读它的时机：判断这次改动是修还是重设计、同一道门连续失败两次、决定质量门槛。

## 三段顺序

先让它能跑，再让它对，最后按实践收尾。三段都按最小改动走，"能跑"不等于"先随便写"。

## 从约束推导，不从惯例推导

设计与规则先问「这个决定由哪几条具体约束推出」。说出具体约束，理由成立；说不出，理由就是惯例。

用法：同一道门两次失败后攻击前提；新需求先问「如果一开始就有这个需求会怎么建」；新规则必须来自实测失败模式，不来自理想实践。

边界：风格与命名跟惯例走，设计与规则从约束推。分界看有没有可查的约束：容量、兼容性、依赖面、维护成本有；命名好不好看没有。

## 不把新需求硬接到旧设计上

新需求与既有设计的形状不合时，先问"如果一开始就有这个需求，会怎么建"，想清楚再分片交付。

判据：这次改动要给旧结构加一个特殊分支，而分支里出现的名词在既有代码和文档里都找不到，就是硬接。

同一个功能在第二个应用点出现第二份实现（两份只差参数或调用方），就是把不同时间点的改动叠成了两套设计。判据：要复制一段既有逻辑再改两行，就是该收敛的信号。

收敛前先查 `git log -- <路径>` 与 `docs/decisions/`。同一处被改过三次就重设计，不再加第四个分支。把历史改动与新需求一起收成一套设计（一个入口、一份实现、参数化差异），再分片交付。

## 两次失败后攻击前提

两个修法共享同一前提，又在同一道门（同一测试、同一验收命令）失败时，按顺序做四件事：

1. 把那个前提写成一句话。
2. 清点哪一方承担了不平衡：谁多做了一步，谁少做了一步。
3. 撤掉那处职责分配或那层依赖，不再加一层判断。
4. 前提没写下来之前，不开第三个修法。

接在编排的第三次重派之前：前两次修实现，第三次先把前提写进 `--retry-note`；写不出前提就转 `blocked`，不再派。

## 让非法状态写不出来

- 用结构表达约束，不用注释和运行时检查。枚举代替字符串，必填项进构造函数，互斥字段合并成一个类型。
- 外部数据在入口解析一次，内部信任解析结果；业务逻辑写成纯函数。
- 外部输入的**形态判断**（`isinstance`、多形态 if、别名 key 尝试）只许出现在归一层。同一个字段在第二个地方猜形状即违规。默认值（`.get(k) or 缺省`）不在此列。归一层自己要有测试，列出它接受的全部形态。
- 不压制编译器的报错。类型错误是信息。

## 幂等

跑两次、或中途崩溃后重跑，终态相同。写状态、建资源、发通知都按这个标准检查。做不到就加显式前置判断（已完成则跳过），不靠"调用方只会调一次"。

## 共享状态先分离再串行

不需要共享的可变状态，各自持有一份。必须共享时只允许一个写者，并在结构上强制（独占写入权、单线程消费），不靠约定。

实例：§5 的记忆归属，`docs/memory/` 由主管独占写入，worker 不写。

## 守卫的生命周期：准入 → 分档 → 举证 → 退出

守卫指门、校验、断言、对账表、棘轮、体检项。四步适用于任何外部输入（模型输出、用户上传、第三方接口），每步的判据都要能在单条 diff 或一次运行输出上判定。

### 准入：三问，缺一不收

1. 它防的那个真实故障发生在哪一次运行？给出可核对的痕迹（项目号、任务号、触发计数、issue）。答「将来可能有人改坏」的不收。
2. 这个故障用户看得见吗？看不见的默认静默（只进日志与诊断，不报红）。
3. 能不能改成结构或测试？能用类型/枚举/schema 表达的优先改结构；代码自己拼错的东西进测试。都不行才留在运行时检查里。

责任归属决定位置：

| 故障来源 | 位置 |
| --- | --- |
| 代码自己拼错（内部一致性） | 测试 |
| 外部输入不合格（模型输出、用户上传、第三方接口） | 运行时检查 |
| 偏好与风格 | 提示词与文档，不进检查 |
| 开发者会忘记同步（登记表、文案表、契约哈希） | `tests/` 或 CI |

三问只用于新增。准入与退出用同一个实验判定：**关掉它，谁会发现？** 答「没人会」的不要建；已经建了的进清理候选。

### 分档：归一 > 回喂重试 > 阻断

每条校验落地时声明属于哪一档，声明不出来按静默处理（只进诊断）。

| 违规类型 | 例子 | 处理 |
| --- | --- | --- |
| 语义唯一，只是词汇或形态不同 | 同义词（`rearview` vs `reverse`）、简写、全半角、大小写、别名 | **归一**，不重试；归一记录进 trace |
| 语义错误，必须模型理解后才能改 | 人物不在本场名单、拍号丢失、台词与剧本不符、秒数越界 | **回喂重试**，reason 给出期望值或闭集，不只说「不合格」 |
| 产物必崩 | 平台会拒、链式产物必坏 | **阻断**，不重试 |

1. 能一一映射的差异不重试。
2. 同一校验项连续成为唯一致败原因时，修法是改提示词或加归一，不是放宽。
3. 触发但总被自动修（归一或重试一次即过）成功的项标「可归一」。
4. 放宽标准前先落决策记录。

### 举证：可以报告，不得自行放宽

既有守卫挡路时报告，不就地绕过：说清它指不出真实故障、它触发的项全被忽略、或者关掉它没人会发现，由人类或主管裁决并落决策记录。不许自行放宽，不许在消费点加兼容分支绕过。

边界：**风格跟惯例，守卫要证据**。既有代码是风格的权威，不是守卫合理性的权威。

### 退出：判据是对照实验

关掉这一项，跑一次真实输入，看三种结局。触发率不作判据。

| 关掉之后 | 结论 | 处置 |
| --- | --- | --- |
| 测试变红 | 防的是正确性 | 留下，并核对是不是该挪到测试侧（准入第 3 问） |
| 产物变了但没人发现 | 防的是偏好 | 降成归一，或直接删 |
| 产物变了且用户看得见 | 必要 | 留下，并核对分档是否正确 |

盘点时机是动作发生时，不建定期流程：重构、换线、给同一处加第二条校验时，对这处做一次对照。存量不追溯，只对挡了你路的那条守卫做实验。

## 测试行为，不测实现

测试的调用方式与真实使用者一致，断言使用者能看到的结果。判据：所有函数都改成返回空值、测试还能通过，这个测试就该删。

## 不显然的活先造工具

同样的手工操作做到第三次，停下来造工具。做法：先手工完整做一个单元，再让工具产出与那个单元逐字一致的结果，之后交给工具。没到第三次不造。

## 单会话的最低审查口径

不派工的改动照做这三条，括号内是派工模式的对应物。

- 验收先于实现（派工单的 `--accept`）：动手前写出「这条改完用什么命令证明对」，写不出就不动第一行。
- 反证一次（DONE 前的强制项）：最后一件事不是跑测试，是把本次新增的一个条件取反跑一遍。转红就还原；仍绿说明新代码没有测试压着，先补测试。
- 独立上下文读 diff（worker 与主管分离）：改动超过三百行或动了共享模块，新开一个会话只给一句「审这个 diff，按五轴」，不带原任务描述。小改动用隔几分钟重读替代，只读代码现在是什么。

## 收尾

- 长任务记动作日志（做了什么、为什么），完成时归入竣工单，不新增常驻文件。
- 主线程只留结论与指针，大块分析外包，回来的只要摘要。
- 提交纪律见 §6；清理与 push 见 `orchestration.md` 的合并流程与 `doctor` 的 `resource-leaks`。

## 可选质量门槛

三个工具（`unclebob/crapper`、`unclebob/dryer`、`unclebob/mutator`）装在机器级，不进项目依赖也不进 git，首次运行自己建 `.venv`。装它们属 `AGENTS.md` §4 的"安装系统级依赖"；不装时按下面的判据人工检查。

| 工具 | 看什么 | 命令 |
| --- | --- | --- |
| crapper | 复杂度热点与 CRAP 分数 | `~/tools/crapper/crapper <目录>...` |
| dryer | 结构重复候选 | `~/tools/dryer/dryer <目录>...` |
| mutator | 变异点与存活数 | `~/tools/mutator/mutator --scan <文件>` |

CRAP = CC² × (1 − 覆盖率)³ + CC。1 到 5 低风险，5 到 30 值得看，30 以上复杂且覆盖不足。**30 以上且落在本次 diff 内的函数，要么拆分，要么说明为什么不拆**。crapper 只读 `coverage/lcov.info`，没有它时只出 CC，Cov% 与 CRAP 显示 N/A。

重复度默认阈值 0.82，达到即列为候选。候选不等于该合并，由人工判断。

变异测试按改动的文件跑，不全量。存活的变异体是缺测试的证据，补测试或删死代码。

触发判据：单次改动增删合计超过 300 行时跑 crapper 与 dryer（派工单「自审」第四步写明命令）。crapper 与 mutator 需要项目 venv 有 `coverage`，缺了会直接报错——报错原文照报，不许手搓替代后不提。

三个工具一律显式给目录。产物落在 `.metrics/`，加进忽略规则。

`doctor` 的 `quality-tools` 检查机器上装没装：缺了报 WARN 不报 FAIL，不影响退出码。
