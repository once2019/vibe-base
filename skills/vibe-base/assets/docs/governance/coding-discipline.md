# 编码纪律（§3 的操作条文）

> 来源：`unclebob/ub-mode`（MIT）中 `AGENTS.md` §3 未覆盖的部分，改写为本仓口径。
> 读它的条件：判断这次改动是修还是重设计、连续两次修法在同一道门失败、或要决定质量门槛时。
> §3 是红线，本文件是操作条文；两者冲突以 `AGENTS.md` 为准。

## 三段顺序

先让它能跑，再让它对，最后按实践收尾。跳段的代价是：对的结构建立在错的形状上，之后每次改动都要付利息。

## 不把新需求硬接到旧设计上

新需求与既有设计的形状不合时，先问"如果一开始就有这个需求，会怎么建"，想清楚再分片交付。

判据：这次改动要给旧结构加一个特殊分支，而分支里出现的名词在设计文档里找不到，就是硬接。

## 两次失败后攻击前提

两个修法共享同一前提，又在同一道门（同一测试、同一验收命令）失败时，停下来做四件事：

1. 把那个前提写成一句话。
2. 数哪个 actor 持有失衡：谁多做了一步，谁少做了一步。
3. 移除那个赋值或那层依赖，而不是再加一层判断。
4. 前提没写下来之前，不开第三个修法。

这条接在编排的第三次失败之前：前两次修实现，第三次先怀疑前提。`blocked` 的任务要在交接说明里写出被推翻的前提。

## 让非法状态写不出来

- 用结构表达约束，不用注释和运行时检查。枚举代替字符串，必填项进构造函数，互斥字段合并成一个类型。
- 外部数据在入口解析一次，内部信任解析结果；业务逻辑写成纯函数。
- 不静默编译器。类型错误是信息，压制它等于把问题推迟到运行期。

## 幂等

跑两次、或中途崩溃后重跑，终态相同。写状态、建资源、发通知都按这个标准检查。做不到就加显式前置判断（已完成则跳过），不靠"调用方只会调一次"。

## 共享状态先分离再串行

不需要共享的可变状态，各自持有一份。必须共享时只允许一个写者，并在结构上强制（独占写入权、单线程消费），不靠约定。

## 测试行为，不测实现

测试的调用方式与真实使用者一致，断言使用者能看到的结果。判据：如果所有函数都改成返回空值、测试还能通过，这个测试就该删。

## 不显然的活先造工具

同样的手工操作做到第三次，停下来造工具。做法：先手工完整做一个单元，再让工具产出与那个单元逐字一致的结果，之后交给工具。

## 收尾

- 每个动作记一行日志（做了什么、为什么），完成时随竣工单一起报。
- 主线程只留结论与指针，大块分析外包，回来的只要摘要。
- 提交小而有序，每条说清为什么、改了什么、怎么证明。
- 清理 worktree 前先确认无人使用；未提交的改动等人决定，不自动删。
- 合并后是否 push 由人决定，覆盖 ub-mode 的"最后推到主线"。

## 可选质量门槛

工具属 `AGENTS.md` §4 的"安装系统级依赖"，不装也能按下面的判据人工检查，装了才有机械证据。

- CRAP < 10：圈复杂度与覆盖率组合，超标就拆函数或补测试。
- 结构重复率 < 0.8：相似度达到阈值的块合并。
- 变异测试：覆盖未覆盖的行，杀掉存活的变异体，删掉死代码。

对应工具是 `unclebob/crapper`、`unclebob/dryer`、`unclebob/mutator`。
