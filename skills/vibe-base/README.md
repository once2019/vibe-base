# vibe-base

给 AI 编程 Agent 用的协作规范。装进项目的是两层东西：治理骨架让每个会话一开始就有记忆、决策和文档的规矩，`init` 之后自动生效；执行编排把规划和实施分开，需要并行时 worker 在独立 worktree 里干活，主管只审结果。两层都落进项目，靠 `AGENTS.md` 驱动，技能删掉也照旧可用。

## 一、问题从哪来

让 agent 干活，麻烦大多出在协作的基本条件上：任务边界、判据、记忆、审查、并行、成本。下面这些与用哪套工具无关。

- 单个会话干不了大任务。上下文随改动累积被挤占，做到后半段时前半段定下的约定已经在窗口边缘了。agent 开始忘记最初的约束，改出来的东西和开头说的目标有偏差，它自己察觉不到。

- 自己审自己等于没人审。同一个会话写代码又做验收，会系统性漏掉自己写错的假设：挑的用例只覆盖它想到的路径，读 diff 看到的是自己的意图而不是文件内容。让人审，人又不可能每分钟都在。

- "做完了"没有判据。agent 说测试通过，可能是三小时前的输出，可能是它新写的一个只覆盖顺利路径的测试，也可能它把失败的用例删了。人得重新跑一遍才能确认。

- 顺序依赖的活只能串着做，人得全程在。改完接口才能改调用方，改完调用方才能补回归。每一步之间人要等报告、判断、再下一条指令，等的时间比干活长。

- 多个会话同时改一个项目，改动互相踩，也互相看不见。两个会话都在动同一个文件，合并时冲突；不冲突也会语义打架，一个删掉的字段另一个还在读。A 在重写渲染管线，B 照着旧接口写调用方，等合起来才发现对不上。共享的 `context.md` 和 `handoff.md` 两个会话都要写，后写的覆盖先写的，新会话读到哪份取决于谁最后保存。

- 主、子 Agent 模式下，子 agent 停住了主 agent 不知道。普通 vibe coding 里常见的分工：主 agent 把活交给子 agent 去另一个终端跑，自己在原地等结果。子 agent 拿不准时可能猜着往下做，也可能停下来等指令；停下来时没有任何信号传回主 agent，主 agent 以为它还在干活。

- 第二天开新会话，它不知道昨天做到哪、试过什么、为什么放弃方案 A，于是重新调研，有时把失败过的路再走一遍。人的补救是写一份进度说明塞进 prompt，越塞越长，最后自己也不维护。

- 规则文件既膨胀又自我矛盾。起初只想写"别删测试"，三个月后 `AGENTS.md` 四百多行，混着构建命令、目录说明、编码风格、临时 workaround。一处说测试必须全绿，另一处说赶时间可以先合，agent 挑对自己有利的那条执行。同一个概念在三处叫三个名字，新接手的人得先花半天对齐术语。

- 决策理由蒸发，文档跟着过期。三个月后有人问"为什么不用 X"，代码里没有答案，聊天记录翻不到，只好再评估一遍，可能得出相反结论。代码改了文档没动，半年后没人知道哪份是现行。

- 危险动作没人把门。引入依赖、删数据、改 CI，agent 有时自己就做了，做完才在报告里提一句。这件事没有集中清单的话，每个会话的理解都不一样。

- 强模型的时间花在杂活上。改文案、批量重命名、补测试这类活，能力强弱差别不大，占用的却是同一条会话、同一份注意力。

## 二、两层机制怎么接住

两层的组织方式一样：常驻层只放红线和目录，细则层放"怎么做"的操作条文。`AGENTS.md` 里是一行指针加行为红线，命令序列、决策档位、审查判据落在项目自己的 `docs/governance/` 下。常驻部分因此能压到一百行以内，每次会话自动生效，不赌技能会不会被想起来。

### 第一层：编程规范与管理

载体是仓库里的文件，不需要通道，也不需要派工。

1. 三层记忆按寿命分开。L1 是 `AGENTS.md`，常驻，只放目录和红线。L2 是 `docs/decisions/`，一条决策一个文件，带理由和被否决的方案，配一份索引。L3 是 `docs/memory/`：`context.md` 记当前状态，`handoff.md` 给下一个会话交接。会话开始时读 context、handoff 和决策索引最近三条，收尾必须写 handoff。

2. 并行会话的写入纪律单独规定：先读最新版，做精确片段替换，禁止整文件覆盖和原地追加。`docs/memory/` 由主管独占写入，worker 不写，它的结论走 DONE 正文，由主管合并后落盘。

3. 规则受预算约束。`AGENTS.md` 不超过 100 行、单行不超过 200 字符，context 不超过 40 行、单行 150 字符，handoff 不超过 60 行、单行 150 字符，超了 `doctor` 的 `governance-budget` 直接 FAIL。收录另有三条铁律：删掉它 agent 会犯错吗，能被 lint 或评审验证吗，有没有实测失败模式作来源。`AGENTS.md` 是唯一事实来源，其他文档只作出处引用。

4. 决策记录回答"为什么不用 X"。每份四节：决定什么，选择理由覆盖四问（解决什么问题、收益、约束、删掉后多久能重建），被否决的方案要具体到技术事实，影响范围写后续约束。建条即登记索引，`doctor` 的 `decisions-index` 双向核对孤儿与死链。

5. 危险动作集中一处。Ask-first 清单只在 `AGENTS.md` §4 维护：引入依赖、装系统级依赖、改 CI 或部署、删数据、force push。其他文档只引用，不复制。

6. 文档与代码同一次提交。需求变更先改 `docs/specs/` 的描述与验收标准，再改代码；新建权威文档先查目录索引，建完立刻登记一行。落点是六处：`AGENTS.md` 放红线，`docs/decisions/` 放决策，`docs/memory/` 放记忆，`docs/progress/` 放竣工单，`docs/specs/` 放规格，`docs/design/` 放设计与调研。

### 第二层：主管 / worker 执行编排

主管是人类直接对话的会话，负责拆分、裁决、审查、合并。worker 是它拉起的子 agent，只实现和上报。两者用消息通道通信，状态落在仓库文件里。

1. 隔离实施。`dispatch` 给每个任务建独立的 worktree 和分支，worker 的改动收敛在自己的分支上，主管拿到完整 diff 而不是口头摘要，合并后删树。多个 worker 之间不会互相覆盖，主管的工作区也始终干净。任务切到"一次能审完"，diff 三百行上下，口子是能否独立验收，不按文件数切。

2. 拆分权留在主管手里。拆分产物就是范围与验收，而这两样正是审查的锚点。范围由 worker 自己定，`scope` 检查就恒真；验收由它自己定，`acceptance` 也恒真，等于自证清白。要下放走两段式：先派只读的拆分任务，验收写成"方案文档存在且列出子项与各自验收命令"，主管审完清单再建实施批次。

3. 决策权分三档。自决是 worker 说了算，实现细节、命名、范围内的小取舍。主管拍板是接口形态、测试策略、换路、重派、拆任务、扩 scope。Ask-first 是 §4 那份清单，必须人类点头，并且要落一份决策记录。

4. 完成定义先于实现。`task new` 两条硬判据：`--scope` 必须列路径，`--accept` 必须是一条可执行命令。写不出验收命令说明需求还没想清。`review` 跑六项检查：越界（`scope`）、密钥（`secrets`）、跳测痕迹（`no-skip`）、空改动（`non-empty`）、验收复跑（`acceptance`）、决策记录（`docs-decisions`），输出存进 `evidence/`，`merge` 之后在主干再跑一次。

5. 异步回合。回合一做体检、建任务、派工，做完就结束回合，不 sleep 不开等待窗口。worker 请示或完成时发消息，通道把主管叫醒，进入回合二跑 `events`。一次 `events` 调用算一轮，连续两轮空等后第三次直接拒绝。

6. 请示与上报是一套固定协议。主、子 Agent 模式缺的就是这条回传路径。worker 只能发三种消息：`ASK`（附问题、选项、推荐项，不许猜）、`DONE`（附摘要、改动文件、自审结论、验证输出、提交）、`ESCALATE`（附已试方案和阻塞点）。发 DONE 前必须自审三样：机械四项（范围、验收、无跳过、无密钥）、五轴过一遍自己的 diff、反证一次。主管按同样口径复核，不采信自报。

7. 并行与批次由代码判定。`dispatch` 比对在跑任务的 scope，相交就拒绝并列出那一对路径，确要重叠加 `--allow-overlap`。有顺序依赖的一串子项整批派给一个 worker，同一棵树里逐项做，每项一个 commit 和一份验收证据，主管只在整批结束时审一次。`--depends-on` 让前置未完成的任务无法派工，它只做门槛，不建 DAG。

8. 失败之后怎么走。一个任务最多派三次，前两次修完重新派工，worker 在同一棵树上接着改，主管看累计 diff；第三次进 `blocked` 交人。重派必须写 `--retry-note` 说明这次改了什么，不带直接拒绝。合并后复跑不过就停在 `merge_ready`，由人决定回退还是修复。

9. 谁能干谁干。跨模块、要读多处既有实现、要判断设计取舍的，给能力强的 agent；机械替换、改文案、补测试，给便宜快的。

10. 命令面是一个纯标准库脚本 `scripts/foreman.py`：`doctor` 体检、`init` 建骨架、`task new` 建任务、`dispatch` 派工、`events` 收协议消息、`reply` 答复、`ask` 立阻塞门、`review` 审 diff 与验收、`merge` 合并归档、`report` 出竣工单、`reconcile` 对账。

### 两层合起来才成立的地方

- 完成判据：编排层给可执行命令和证据文件，治理层给审查口径（六项机械检查加五轴读 diff）和反证要求。只有命令没有口径，会合并一份测试全绿但结构更糟的改动。

- 并行：编排层给隔离树、scope 拦截、前置门槛，治理层给记忆写入归属和术语唯一。少了前者改动互相踩，少了后者代码不冲突但文档和状态各记一份。

- 危险动作：编排层给 `ASK` 协议和阻塞门，治理层给清单本身和 `reply --decision-doc` 硬闸，`review` 的决策记录检查是第二道网。缺一层，绕过就成立。

## 三、理论支撑与取舍

### 第一层：规范从哪来

1. 理念来自 Karpathy 的三套公开写作。Guidelines 管 Agent 写代码的常见病，落到 `AGENTS.md` §3 那几条。LLM Wiki 管知识积累，调研结论、方案比较、根因分析写进 `docs/design/`，被否决的方案写进 `docs/decisions/`，下次直接查。受控文字管沟通，同一个概念只许一个名字，"尽快处理"必须换成具体日期。三套背后有共同的元设计：规则必须来自实测失败模式，每条配一个能自查的问句，每条要承认自己的代价。

2. 可判定优先。一条规则能不能被机器或评审检验，决定它算不算规则。"注意代码质量"不是规则，"提交前 ruff、mypy、pytest 全部通过并贴出本次输出"是规则。代价是有些本该模糊的判断被压成机械判据，偶尔误报，处理办法是给误报留显式出口。

### 第二层：编排从哪来

3. 主管 / worker 的形态是监督树（supervision tree）。Erlang/OTP 里 supervisor 只做三件事：启动 child、收 child 的退出信号、按策略决定重启还是放弃。主管对应 supervisor，worker 对应 child，差别在于 worker 的退出信号要靠消息通道送出来，通道不可靠时就得补探测，`reconcile` 干的就是这件事。三次上限是重启强度限制：超过就升级给人，不再自动重启。

4. 生成与验证分离来自职责分离（separation of duties）和四眼原则。内控里同一人不能既执行又审批，软件工程里对应 code review。放到 agent 上还多一层实证理由：模型评自己的输出会偏向自己，LLM-as-judge 研究里叫自我偏好（self-preference）。所以 worker 自审只是初筛，主管必须独立复核，`review` 的六项检查是复核的固定口径。

5. worktree 隔离对应数据库的隔离级别和"隔离实施、串行合并"。并行写同一个工作区，失败模式是任意时刻互相覆盖，冲突点不可预测。给每个任务一棵独立的树，并发写就降级成合并点上的串行比较：冲突只在 `merge` 时出现，且以 diff 形式可见。这与 CI 给每个变更起独立构建环境同源，代价是多一份磁盘和一次合并。

6. 消息通道对应 actor 模型的消息传递。actor 之间不共享内存，只发消息，好处是解耦，代价是投递语义不确定：消息会丢、会重复、会被第三方读走。所以状态不能靠消息推导，`task.json` 才是事实源，消息只负责唤醒和携带证据指针。至少一次投递配上幂等写入，重复消费才不会写坏状态。

7. 回合制对应事件驱动替代轮询。轮询实现简单，代价是空转和延迟；事件驱动省掉空转，代价是需要一条可靠通道。会话不能常驻等待，所以派工后结束回合，消息到了再唤醒。两轮空等的上限挡住的是"没有消息"被当成"还在跑"。

8. 验收先于实现来自 ATDD 与可执行规格。验收写成能跑的命令，需求模糊时这条命令就写不出来，模糊在这一步暴露，而不是在合并时暴露。`task new` 强制 `--accept`，把完成的定义从形容词变成可执行文件。

9. 谁能干谁干对应比较优势与模型路由。判断设计取舍的活交给强模型，机械替换交给便宜快的，因为前者的差别在于判断质量，后者只在于速度和单价。批次任务同源：一串顺序依赖的子项共用一次派工和一次审查，固定开销被摊薄。

### 两条通用取向

10. 机制自己也会坏。`reconcile` 拿通道的权威事实对三条账：通道说完成而状态机还在跑、worker 已退出但没上报、消息被读走却没有对应证据。合并后的清理先落盘状态再执行，失败只记结果，`doctor` 的 `resource-leaks` 报残留。这些护栏不解决工程问题，只保证解决工程问题的机制不先坏掉。

11. 整套体系偏向正确而不是速度。证据门槛会否决一部分"感觉对"的改进，细则加载和自查拖慢写作节奏，常驻部分占用不到一百行上下文。

| 选择                       | 换来            | 代价                           |
| ------------------------ | ------------- | ---------------------------- |
| 占位符回填制                   | 冷启动不追问用户      | 骨架长期留 `<...>`，靠后续会话自觉        |
| `foreman.py` 单文件约 2900 行 | 复制即用、零依赖、单处审计 | 文件大，改动要跳段落                   |
| 编排能力随骨架发（16 个文件）         | 一个技能、一次安装     | 新项目多一个可能不用的脚本                |
| 项目自持副本                   | 删掉技能照旧可用      | 不随技能升级，要 `--force` 或人工对照     |
| 根目录与 assets 用符号链接        | 一份实体，零漂移      | Windows 检出要开 `core.symlinks` |
| worktree 而非切换分支         | 并行写互不干扰，冲突集中在合并点 | 每个任务一份磁盘与一次合并                |
| 消息通道而非轮询状态文件           | 有权威投递记录，能对账   | 依赖通道可用，通道挂了要探测兜底             |
| 重派上限三次                  | 卡住的任务一定交到人手上  | 前两次可能白做                      |
| 批次任务                     | 只审一次，省往返      | diff 更长，第 3 项失败整批回退          |
| 默认主管拆任务                  | 审查锚点成立        | 主管带宽成为瓶颈                     |
| `events` 不设逃生门           | 规则不会被绕过       | 探测失败时可能多等一轮                  |
| 合并后不自动 push              | 人保留最后决定权      | 每次要手动推                       |

## 四、什么时候用

适合这几种情况：

- 有可执行的验收命令，测试、lint、构建能跑。
- 任务能拆到"一次能审完"，diff 三百行上下。
- 需要多任务并行，且互相隔离。
- 项目长期维护，决策要能追溯。
- 多个 Agent 或多人交替接手同一个仓库。
- 存在不可逆动作，需要人把关。

不适合的：

- 改一行文案、改个变量名。派活的开销是收益的十倍。
- 需求还在模糊期，先问清楚，否则派出去的是猜。
- 需要人在旁边频繁做品味判断，阻塞门会占满人类带宽。
- 跨仓库改动，一棵树装不下。
- 一次性脚本。
- 没有测试基础设施的项目。验收命令写不出来，整套审查就没有锚点。

## 五、开始使用
```bash

mkdir -p ~/.agent/skills
cp -r skills/vibe-base ~/.agent/skills/

```

装好之后，新项目里说一句「初始化项目治理」或「init AGENTS」。产出 16 个文件（1 份 `AGENTS.md`、14 份 docs、1 个 `scripts/foreman.py`），外加空的 `.vibe/` 骨架和忽略规则。幂等，不覆盖已有文件；占位符不追问，agent 在后续开发中自己回填。初始化之后技能可以删掉。

`init` 之后先做三件事：填掉 `AGENTS.md` 里测试、lint、类型检查三条命令，给第一个任务写一条真能跑的验收命令，跑一次 `doctor` 修红项。记忆和决策库随开发长起来，编排在第一次真要并行时再启用。

决策数到 20 条时 `doctor` 会提示跑复盘，正本是项目里的 `docs/governance/governance-review.md`。
