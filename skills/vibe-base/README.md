# vibe-base

给 AI 编程 Agent 用的协作规范。装进项目的是两层东西：治理骨架让每个会话一开始就有记忆、决策和文档的规矩，`init` 之后自动生效；执行编排把规划和实施分开，需要并行时 worker 在独立 worktree 里干活，主管只审结果。两层都落进项目，靠 `AGENTS.md` 驱动，技能删掉也照旧可用。

## 一、问题从哪来

让 agent 干活，麻烦大多出在协作的基本条件上：任务边界、判据、记忆、审查、并行、成本。下面这些与用哪套工具无关。

- 单个会话干不了大任务。上下文随改动累积被挤占，做到后半段时前半段定下的约定已经在窗口边缘了。agent 开始忘记最初的约束，改出来的东西和开头说的目标有偏差，它自己察觉不到。

- 自己审自己等于没人审。同一个会话写代码又做验收，会系统性漏掉自己写错的假设：挑的用例只覆盖它想到的路径，读 diff 看到的是自己的意图而不是文件内容。让人审，人又不可能每分钟都在。

- "做完了"没有判据。agent 说测试通过，可能是三小时前的输出，可能是它新写的一个只覆盖顺利路径的测试，也可能它把失败的用例删了。人得重新跑一遍才能确认。

- 顺序依赖的活只能串着做，人得全程在。改完接口才能改调用方，改完调用方才能补回归。每一步之间人要等报告、判断、再下一条指令，等的时间比干活长。

- 多个会话同时改一个项目，改动互相踩，也互相看不见。两个会话都在动同一个文件，合并时冲突；不冲突也会语义打架，一个删掉的字段另一个还在读。A 在重写渲染管线，B 照着旧接口写调用方，等合起来才发现对不上。共享的 `context.md` 和 `handoff.md` 两个会话都要写，后写的覆盖先写的，新会话读到哪份取决于谁最后保存。

- 主、子 Agent 模式下，子 agent 停住了主 agent 不知道。普通 vibe coding 里常见的分工：主 agent 把活交给子 agent 去另一个终端跑，自己在原地等结果。子 agent 拿不准时可能猜着往下做，也可能停下来等指令；停下来时没有任何信号传回主 agent，主 agent 以为它还在干活。

- 记忆不跨会话。第二天开新会话，它不知道昨天做到哪、试过什么、为什么放弃方案 A，于是重新调研，有时把失败过的路再走一遍。人的补救是写一份进度说明塞进 prompt，越塞越长，最后自己也不维护。

- 规则文件既膨胀又自我矛盾。起初只想写"别删测试"，三个月后 `AGENTS.md` 四百多行，混着构建命令、目录说明、编码风格、临时 workaround。一处说测试必须全绿，另一处说赶时间可以先合，agent 挑对自己有利的那条执行。同一个概念在三处叫三个名字，新接手的人得先花半天对齐术语。

- 决策理由蒸发，文档跟着过期。三个月后有人问"为什么不用 X"，代码里没有答案，聊天记录翻不到，只好再评估一遍，可能得出相反结论。代码改了文档没动，半年后没人知道哪份是现行。

- 危险动作没人把门。引入依赖、删数据、改 CI，agent 有时自己就做了，做完才在报告里提一句。这件事没有集中清单的话，每个会话的理解都不一样。

- 强模型的时间花在杂活上。改文案、批量重命名、补测试这类活，能力强弱差别不大，占用的却是同一条会话、同一份注意力。

## 二、两层机制怎么接住

两层的组织方式一样：常驻层只放红线和目录，细则层放"怎么做"的操作条文。`AGENTS.md` 里是一行指针加行为红线，命令序列、决策档位、审查判据落在项目自己的 `docs/governance/` 下。常驻部分因此能压到一百行以内，每次会话自动生效，不赌技能会不会被想起来。

### 第一层：编程规范与管理

载体是仓库里的文件，不需要通道，也不需要派工。

1. 三层记忆按寿命分开。L1 是 `AGENTS.md`，常驻，只放目录和红线。L2 是 `docs/decisions/`，一条决策一个文件，带理由和被否决的方案，配一份索引。L3 是 `docs/memory/`：`context.md` 记当前状态，`handoff.md` 给下一个会话交接。会话开始时读 context、handoff 和决策索引最近三条，收尾必须写 handoff。

2. 并行会话写记忆文件有纪律：先读最新版，做精确片段替换，禁止整文件覆盖和原地追加。`docs/memory/` 由主管独占写入，worker 不写，它的结论走 DONE 正文，由主管合并后落盘。

3. 规则受预算约束。`AGENTS.md` 不超过 100 行、单行不超过 200 字符，context 不超过 40 行、单行 150 字符，handoff 不超过 60 行、单行 150 字符，超了 `doctor` 的 `governance-budget` 直接 FAIL。收录另有三条铁律：删掉它 agent 会犯错吗，能被 lint 或评审验证吗，有没有实测失败模式作来源。`AGENTS.md` 是唯一事实来源，其他文档只作出处引用。

4. 决策记录回答"为什么不用 X"。每份四节：决定什么，选择理由覆盖四问（解决什么问题、收益、约束、删掉后多久能重建），被否决的方案要具体到技术事实，影响范围写后续约束。建条即登记索引，`doctor` 的 `decisions-index` 双向核对孤儿与死链。

5. 危险动作集中一处。Ask-first 清单只在 `AGENTS.md` §4 维护：引入依赖、装系统级依赖、改 CI 或部署、删数据、force push。其他文档只引用，不复制。

6. 编码纪律单独成篇。`AGENTS.md` §3 是红线，操作条文在 `docs/governance/coding-discipline.md`：三段顺序（先能跑、再对、最后收尾）、单会话的最低审查口径（验收先行、反证一次、独立上下文读 diff），加八条 §3 没覆盖的判据。判断这次改动是修还是重设计看两条判据：要加的特殊分支里出现既有代码和文档都找不到的名词，就是硬接；同一个功能在第二个应用点出现第二份实现、两份只差参数或调用方，是把不同时间点的改动叠成了两套设计，先查 `git log` 与 `docs/decisions/` 再决定收敛还是新建。同一道门连续两次失败，先把两个修法共享的那个前提写成一句话，再开第三个修法，写不出前提就转 `blocked`。剩下五条是让非法状态写不出来、幂等、共享状态单写者、测行为不测实现（所有函数返回空值测试还能过就删）、同一手工活做到第三次才造工具。

7. 文档与代码同一次提交。需求变更先改 `docs/specs/` 的描述与验收标准，再改代码；新建权威文档先查目录索引，建完立刻登记一行。落点是六处：`AGENTS.md` 放红线，`docs/decisions/` 放决策，`docs/memory/` 放记忆，`docs/progress/` 放竣工单，`docs/specs/` 放规格，`docs/design/` 放设计与调研。

### 第二层：主管 / worker 执行编排

主管是人类直接对话的会话，负责拆分、裁决、审查、合并。worker 是它拉起的子 agent，只实现和上报。两者用消息通道通信，状态落在仓库文件里。

1. 隔离实施。`dispatch` 给每个任务建独立的 worktree 和分支，worker 的改动收敛在自己的分支上，主管拿到完整 diff 而不是口头摘要，合并后删树。多个 worker 之间不会互相覆盖，主管的工作区也始终干净。新树缺主仓的 `.env`/`.venv` 会让第一次验收假红，所以在 `worktree_links` 里登记要带过去的路径，`dispatch` 建树后自动软链。任务切到"一次能审完"，diff 三百行上下，口子是能否独立验收，不按文件数切。

2. 拆分权留在主管手里。拆分产物就是范围与验收，而这两样正是审查的锚点。范围由 worker 自己定，`scope` 检查就恒真；验收由它自己定，`acceptance` 也恒真，等于自证清白。要下放走两段式：先派只读的拆分任务，验收写成"方案文档存在且列出子项与各自验收命令"，主管审完清单再建实施批次。

3. 决策权分三档。自决是 worker 说了算，实现细节、命名、范围内的小取舍。主管拍板是接口形态、测试策略、换路、重派、拆任务、扩 scope。Ask-first 是 §4 那份清单，必须人类点头，并且要落一份决策记录。

4. 完成定义先于实现。`task new` 两条硬判据：`--scope` 必须列路径，`--accept` 必须是一条可执行命令。写不出验收命令说明需求还没想清。`review` 跑六项检查：越界（`scope`）、密钥（`secrets`）、跳测痕迹（`no-skip`，声明环境前置的跳过带 `env-skip` 标记即放行，放行照报）、空改动（`non-empty`）、验收复跑（`acceptance`）、决策记录（`docs-decisions`），输出存进 `evidence/`，`merge` 之后在主干再跑一次。

5. 异步回合。回合一做体检、建任务、派工，做完就结束回合，不 sleep 不开等待窗口。worker 请示或完成时发消息，通道把主管叫醒，进入回合二跑 `events`。一次 `events` 调用算一轮，连续两轮空等后第三次直接拒绝。每次 `events` 输出末尾都重申还在等人拍板的事项，处理 worker 交接时不会把它们滚忘。

6. 请示与上报是一套固定协议。主、子 Agent 模式缺的就是这条回传路径。worker 只能发三种消息：`ASK`（附问题、选项、推荐项，不许猜）、`DONE`（附摘要、改动文件、自审结论、验证输出、提交）、`ESCALATE`（附已试方案和阻塞点）。发 DONE 前必须自审三样：机械四项（范围、验收、无跳过、无密钥）、五轴过一遍自己的 diff、反证一次。主管按同样口径复核，不采信自报。

7. 并行与批次由代码判定。`dispatch` 比对在跑任务的 scope，相交就拒绝并列出那一对路径，确要重叠加 `--allow-overlap`。有顺序依赖的一串子项整批派给一个 worker，同一棵树里逐项做，每项一个 commit 和一份验收证据，主管只在整批结束时审一次。`--depends-on` 让前置未完成的任务无法派工，它只做门槛，不建 DAG。

8. 失败之后怎么走。一个任务最多派三次，前两次修完重新派工，worker 在同一棵树上接着改，主管看累计 diff；第三次进 `blocked` 交人。重派必须写 `--retry-note` 说明这次改了什么，不带直接拒绝。`blocked` 有出口：`task unblock --reason` 说清根因后回到可派工，重派仍要 `--retry-note`；判断根因不在实现层、要重走满三次时加 `--reset-attempts`。审查不通过落到 `failed` 后可以再审一次（`review` 接受 `failed`，修完直接重跑，不必重派）。合并后复跑不过就停在 `merge_ready`，由人决定回退还是修复。

9. 谁能干谁干。跨模块、要读多处既有实现、要判断设计取舍的，给能力强的 agent；机械替换、改文案、补测试，给便宜快的。

10. 命令都走一个纯标准库脚本 `scripts/foreman.py`：`doctor` 体检、`init` 建骨架、`task new` 建任务、`dispatch` 派工、`events` 收协议消息、`reply` 答复、`ask` 立阻塞门、`review` 审 diff 与验收、`reject` 打回（五轴不过时）、`merge` 合并归档（连同淘汰 attempt 的树与分支）、`report` 出竣工单、`reconcile` 对账、`task unblock` 人工解锁、`task abandon` 放弃派工。

### 两层合起来才成立的地方

- 完成判据：编排层给可执行命令和证据文件，治理层给审查口径（六项机械检查加五轴读 diff）和反证要求。只有命令没有口径，会合并一份测试全绿但结构更糟的改动。

- 并行：编排层给隔离树、scope 拦截、前置门槛，治理层给记忆写入归属和术语唯一。少了前者改动互相踩，少了后者代码不冲突但文档和状态各记一份。

- 危险动作：编排层给 `ASK` 协议和阻塞门，治理层给清单本身和 `reply --decision-doc` 硬闸，`review` 的决策记录检查是第二道网。缺一层，绕过就成立。

## 三、理论支撑与取舍

### 第一层：规范从哪来

1. 三套理念都来自 Karpathy 的公开写作，各管一件事。Guidelines 治 agent 写代码的常见病，落到 `AGENTS.md` §3。LLM Wiki 治知识积累，调研结论写进 `docs/design/`，被否决的方案写进 `docs/decisions/`。受控文字治沟通，一个概念只许一个名字，"尽快处理"要换成具体日期。三条共同的底线：规则从实测失败里来，每条配一个能自查的问句，每条承认自己的代价。

2. 一条规则要能被检验才算规则。"注意代码质量"没法检验，"提交前 ruff、mypy、pytest 全过并贴出本次输出"可以。代价是模糊判断被压成机械判据，偶尔误报，所以给误报留了显式出口。

3. 奥卡姆剃刀与第一性原理是同一个决定的两问，一个问凭什么加，一个问删掉会怎样。剃刀换个对象问同一个问句：代码问删掉这段会不会少解决问题，规则问删掉这行 agent 会不会犯错，文档问同类权威是不是已经有一份。第一性原理要求说出这个决定由哪几条具体约束推出，说不出，理由其实是「别人这么做」。风格跟惯例走，设计与规则从约束推。代价是遇模糊需求偏保守，所以配套一条「先问清再动手」，把不确定性花在提问上而不是搭架子上。

4. 编码纪律来自 `unclebob/ub-mode`（MIT），只收它 `AGENTS.md` §3 没覆盖的判据，不收它的技能形态。四处没有照搬：它的「最后推到主线」与本仓「合并后不自动 push」相反；它没有记忆、决策与 Ask-first，本仓有，两者是上下游；三个质量门槛工具要装系统级依赖，列为可选；它的日志格式与本仓的 evidence 和竣工单重复，只留「长任务日志随竣工单报」这一层。

### 第二层：编排从哪来

1. 主管 / worker 照的是 Erlang 的监督树。supervisor 只做三件事：拉起 worker、收它的退出信号、决定重启还是放弃。这里的差别是退出信号要靠消息送出来，通道不可靠就得自己探测，`reconcile` 就是那个探测。三次上限对应重启强度，超了交人。

2. 写的人和验的人分开。内控里同一个人不能既执行又审批，软件里就是 code review。agent 还多一条理由：模型评自己的输出会偏心。所以 worker 自审只是初筛，主管必须独立复核，`review` 六项是固定口径。

3. 每个任务一棵独立的 worktree。并行写同一个目录，失败模式是任意时刻互相覆盖，冲突点不可预测；分开之后冲突只在 `merge` 时出现，以 diff 摆出来。CI 给每个变更起独立构建环境是同一个思路，代价是多一份磁盘和一次合并。

4. 消息通道借的是 actor 模型的做法：彼此不共享内存，只发消息。好处是解耦，代价是投递不可靠，消息会丢、会重复、会被别人读走。所以状态不能从消息推导，`task.json` 才是事实源，消息只负责唤醒。同一份状态写两遍和写一遍结果相同，重复消费才写不坏。

5. 回合制是事件驱动替掉轮询。轮询简单但空转，事件驱动省空转但要可靠通道。会话不能常驻等待，所以派工后结束回合，消息到了再唤醒。两轮空等的上限，挡的是把"没消息"当成"还在跑"。

6. 先写验收再动手。验收写成能跑的命令，需求模糊时这条命令写不出来，模糊在派工前就暴露。`task new` 强制 `--accept` 就是这个作用。

7. 判断的活给强模型，搬砖的活给便宜的。改文案、批量重命名、补测试，模型强弱差别不大，占的是同一份注意力。批次任务同理：一串有顺序的子项共用一次派工和一次审查，派工与审查的固定开销只付一次。

### 两条通用取向

1. 机制自己也会坏。`reconcile` 拿通道的权威事实对三条账：通道说完成而状态机还在跑、worker 已退出但没上报、消息被读走却没有对应证据。合并后的清理先落盘状态再执行，失败只记结果，`doctor` 的 `resource-leaks` 报残留。这些护栏不解决工程问题，只保证机制不先坏掉。

2. 整套体系偏向正确而不是速度。证据门槛会否决一部分"感觉对"的改进，细则加载和自查拖慢节奏，常驻部分占用不到一百行上下文。

| 选择                       | 换来            | 代价                           |
| ------------------------ | ------------- | ---------------------------- |
| 项目自持副本                   | 删掉技能照旧可用      | 不随技能升级，要 `--force` 或人工对照     |
| 根目录与 assets 用符号链接        | 一份实体，零漂移      | Windows 检出要开 `core.symlinks` |
| `events` 不设逃生门           | 规则不会被绕过       | 探测失败时可能多等一轮                  |
| 合并后不自动 push              | 人保留最后决定权      | 每次要手动推                       |

## 四、依赖

编程规范与管理这一层不挑 Agent，也不挑 IDE。编排能力（主管 / worker 模式）有两种跑法，任选其一，用哪个由你定，`init` 只打印命令，本技能不安装任何依赖，下面列的可选项也一样。

通用模式在终端里用，靠 hcom 这个命令行工具，任何 CLI 类型的 agent 都能跑，没有 daemon。

Orca 模式在 Orca 里用，通信和事件驱动走 Orca 自己的能力，主管会话必须在 Orca 管辖的终端里启动。

另有一组可选的质量门槛工具，装在机器级 `~/tools/`，属系统级依赖，首次运行自己建 `.venv`：

```bash
git clone https://github.com/unclebob/crapper ~/tools/crapper
git clone https://github.com/unclebob/dryer   ~/tools/dryer
git clone https://github.com/unclebob/mutator ~/tools/mutator
```

| 工具 | 看什么 | 命令 |
| --- | --- | --- |
| crapper | 复杂度热点与 CRAP 分数 | `~/tools/crapper/crapper <目录>...` |
| dryer | 结构重复候选 | `~/tools/dryer/dryer <目录>...` |
| mutator | 变异点与存活数 | `~/tools/mutator/mutator --scan <文件>` |

不装也能按 `docs/governance/coding-discipline.md` 的人工判据检查，`doctor` 的 `quality-tools` 报 WARN 不报 FAIL，不影响退出码。两条坑：不传目录时工具会向上找根，可能扫到项目外的文件，一律显式给目录；产物落在 `.metrics/`，要进忽略规则。

控制面脚本 `scripts/foreman.py` 是纯标准库，Python 3.9+ 可跑。

## 五、什么时候用

适合这几种情况：

- 有可执行的验收命令，测试、lint、构建能跑。
- 任务能拆到"一次能审完"，diff 三百行上下。
- 需要多任务并行，且互相隔离。
- 项目长期维护，决策要能追溯。
- 多个 Agent 或多人交替接手同一个仓库。
- 存在不可逆动作，需要人把关。

不适合的：

- 改一行文案、改个变量名。派活的开销是收益的十倍。
- 需求还在模糊期，先问清楚，否则派出去的是猜。
- 需要人在旁边频繁做品味判断，阻塞门会占满人类带宽。
- 跨仓库改动，一棵树装不下。
- 一次性脚本。
- 没有测试基础设施的项目。验收命令写不出来，整套审查就没有锚点。

## 六、开始使用

```bash
mkdir -p ~/.pi/agent/skills          # pi
cp -r skills/vibe-base ~/.pi/agent/skills/

mkdir -p ~/.codex/skills             # codex
cp -r skills/vibe-base ~/.codex/skills/
```

装好之后，新项目里说一句「初始化项目治理」或「init AGENTS」。产出 17 个文件（1 份 `AGENTS.md`、15 份 docs、1 个 `scripts/foreman.py`），外加 `.vibe/` 骨架和忽略规则。忽略规则写进 `.git/info/exclude`，不随仓库分发，所以每个克隆各自跑一次 `init`，否则 `.vibe/` 的状态文件会进提交。幂等，不覆盖已有文件；占位符不追问，agent 在后续开发中自己回填。初始化之后技能可以删掉。

`init` 之后先做三件事：填掉 `AGENTS.md` 里测试、lint、类型检查三条命令，给第一个任务写一条真能跑的验收命令，跑一次 `doctor` 修红项。记忆和决策库随开发长起来，编排在第一次真要并行时再启用。

决策数到 20 条时 `doctor` 会提示跑复盘，正本是项目里的 `docs/governance/governance-review.md`。
