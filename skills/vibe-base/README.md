# vibe-base

给 AI 编程 Agent 用的协作规范，主体来自 Karpathy 的三套公开理念，经日常高强度使用的实战打磨、迭代升级后固化成型。

技能里装了两套能力。治理骨架让项目一开始就有记忆、决策和文档的规矩，此后每个会话自动生效；执行编排把规划和实施分开，需要并行推进几件事时，worker 在独立的 worktree 里干活，主管只审结果。骨架在 init 那一刻就位，编排用到才启用。两者都落进项目，靠 AGENTS.md 驱动，不依赖技能还在不在。

## 三套底层理念

这三套都出自 Karpathy 的公开写作，各管一层：Agent 的行为、知识的积累、沟通的质量。

### Guidelines：治 Agent 写代码的常见病

Karpathy 观察 LLM 写代码的翻车姿势，归结成四条规则：

- 动手前把假设说清楚。多种理解并存时全部摆出来，别偷偷挑一个。
- 只写解决问题的最小代码。没人要的抽象、配置项、"以防万一"的异常处理，一律不加。
- 外科手术式修改。每一行变更都能追溯到用户的请求；不顺手"改进"旁边的代码，既有死代码看见了要说，但不动手删。
- 先定义怎么算完成，再动手。修 bug 就先写复现测试，重构就保证前后测试都绿。

这套东西里更值钱的其实是元设计：规则必须来自实测的失败模式，不能从理想实践往下推；每条规则要配一个能自查的问题（"这行改动是用户要的吗？"）；每条规范要承认自己的代价，比如"偏向谨慎，牺牲速度"。

### LLM Wiki：把知识编译成持续维护的维基

大多数人用 LLM 处理文档是 RAG 的路子：问一次，查一次，拼一次，什么都没留下。Karpathy 的说法是反过来，让 LLM 把知识"编译"进一个持续维护的维基。新资料进来，读透、摘要点、更新相关页面、标出新旧矛盾；查询得到的分析也回填进去。输入和探索都在复利。

落到项目里，它解决的是同一份知识被反复重新推导。调研结论、方案比较、根因分析、被否决的替代方案，都写成文档留在仓库，下次碰到同类问题直接查，不用从头再问一遍。分析产物本身也回填：写完的设计文档反过来影响下一次决策，越用越厚。

这套模式有三个动作：消化新源，查询回填，定期体检（抓矛盾、过期、孤儿页）。它成立的前提就一条：知识库的常见死因是没人维护，而维护恰恰是 LLM 不嫌烦的那部分工作。

### 受控文字：沟通也要有硬约束

空客的维修手册用一套叫 ASD-STE100 的受控英语：句长有上限，一个动词只许一个意思，歧义词禁用。Karpathy 拿它说明一个趋势：LLM 越强，人的工作越往"理解"上移，而理解的介质是可以换的，从受控文字，到图，到交互网页，再到按需生成、用完即弃的讲解视频。

落到编程协作，最直接的是前半段：Agent 跟人的沟通也该受控。同一个概念只许一个名字，一句话只说一件事，"尽快处理"必须换成具体日期。

## 体系怎么分层

两套能力共用一种分法：常驻层只放红线和目录，细则层放"怎么做"的操作条文。行为红线每次会话都生效，不赌语义触发；细则不藏在技能触发链里，init 时随骨架实例化到项目 `docs/governance/`，AGENTS.md 的指针直接指过去，会话最多只加载 100 行内容。

| 理念         | 常驻层（AGENTS.md，每次会话生效） | 细则层（项目 docs/governance/ 实例，由 AGENTS.md 指针直达） |
| ---------- | --------------------- | -------------------------------------------- |
| Guidelines | §3 四条行为规则             | 收录铁律，三条元设计管规则演化                              |
| LLM Wiki   | §6 文档目录给分析产物留了家       | 回填路由；复盘信号新增知识体检                              |
| 受控文字       | §3 沟通受控一行             | 行文受控节                                        |

执行编排按同样的分法铺开，多出一层过程态：

| 层   | 内容                  | 落在哪                                | 入 git |
| --- | ------------------- | ---------------------------------- | ----- |
| 常驻  | 什么时候启用、怎么开口、默认不派工   | `AGENTS.md` 一行指针                   | 是     |
| 细则  | 命令序列、决策档位、落点分工、审查判据 | 项目 `docs/governance/` 编排三份         | 是     |
| 过程态 | 任务状态、派工单、验收证据、隔离树   | `.vibe/`，init 建骨架，派工后才写状态         | 否     |
| 终态  | 竣工单、Ask-first 裁决    | `docs/progress/`、`docs/decisions/` | 是     |

## 能力一：治理骨架

人和 Agent 一起干活，出问题的地方大多不在代码里。代码写错，测试和评审还能拦；拦不住的是"上次为什么这么定"没人记得，是"这条规则以哪份为准"说不清。人类团队靠人脑、口头和评审把这些兜住，Agent 没有这份连续性，每次会话都像新人第一天上班，还不记得昨天谈过什么。

这套体系补的就是这一层：把靠人记住的东西写成文件。决策连同被否决的方案一起留档，状态快照只记当下，规则只留一份。Agent 开工前读这几处，等于把团队的交接流程接进了它的工作循环。

省事也省在这里。小于 100 行的常驻规则每次会话自动生效，不依赖外部记忆系统或向量库；换会话、换 IDE、换 Agent 都不丢，因为记忆和决策就放在仓库里；意图讨论、决策历史、规格标准随项目走，多人多会话看到的是同一份。

边界也说清楚：一次性任务、单人小脚本，这套东西是负担。它回本靠的是同一批上下文被反复使用，项目活得越久、换的会话越多，越划算。

落到文件上是六处：`AGENTS.md` 放红线和目录；`docs/decisions/` 一条决策一个文件，带理由和被否决的方案；`docs/memory/` 放状态快照与跨会话交接；`docs/progress/` 放进度与竣工单；`docs/specs/` 放需求规格；`docs/design/` 放设计文档。怎么填才算合格看 `docs/governance/` 下的细则，`AGENTS.md` 的指针直接指过去。

## 能力二：执行编排（规划与实施分离）

骨架管"怎么记、怎么定"，编排管"怎么同时推进几件事"。它由角色、决策权、状态、审查门槛四部分组成，用到了才启用。

主管是你正在对话的那个会话，只有一个。它拆任务、写派工单、拍板、审结果、合并，不写业务代码。worker 是派工时拉起的子 agent，在独立的 git worktree 里实现，只改范围内的文件，不碰合并权；上报完成前先自审：机械四项（范围、验收、无跳过、无密钥）、五轴过一遍自己的 diff、反证一次（取反新增条件看测试是否转红），修完再发 DONE；主管收到后按同样口径复核，结论标严重度。

决策权分三档。实现细节由 worker 自决；接口形态、测试策略、重派、拆任务这类由主管拍板；`AGENTS.md` §4 那份 Ask-first 清单里的事必须人类点头。前两档在过程态里留痕，第三档还要落一份决策记录。

任务状态跑在 `.vibe/tasks/<id>/task.json`，这是过程态里唯一的事实源。派工单、验收证据、隔离树、归档都在 `.vibe/` 下，本地忽略、不入库，合并后随归档退场。留下的东西有两样：`docs/progress/` 的竣工单，`docs/decisions/` 的裁决。`docs/memory/` 由主管独占写，worker 只改代码。

命令面是一个脚本，纯标准库：

| 命令                                                                     | 做什么                                              |
| ---------------------------------------------------------------------- | ------------------------------------------------ |
| `doctor`                                                               | 体检 git、编排通道、agent、会话身份、仓库是否干净、AGENTS 预算与决策索引双向一致 |
| `init`                                                                 | 建 `.vibe/` 并写忽略规则，幂等                             |
| `task new` / `task set-acceptance` / `task set-scope` / `task abandon` | 建任务、改验收命令、调允许改动的范围、放弃                            |
| `dispatch`                                                             | 建分支与 worktree，拉起 worker，然后主管结束回合                 |
| `events`                                                               | 阻塞等一条协议消息（ASK / DONE / ESCALATE）                 |
| `reply`                                                                | 把裁决发回 worker；Ask-first 裁决必须带 `--decision-doc`    |
| `ask`                                                                  | 立阻塞门，任务挂起等人                                      |
| `review`                                                               | 取 diff、跑验收、存证据，给 `merge_ready` 或 `failed`        |
| `merge`                                                                | 合并、复跑验收、删树、归档                                    |
| `report`                                                               | 出竣工单，写进 `docs/progress/`                         |

审查门槛有三道：

- 验收命令先于派工存在。派工单里写不清"怎么算完成"，worker 会自己编一个。
- Ask-first 裁决必须落决策记录。`reply` 时不带 `--decision-doc` 直接被拒，`review` 再查一遍，登记过的文件后来被删了也过不去。
- 审查只信 diff 与证据。范围、密钥、跳测痕迹、验收复跑、决策记录都由代码判定；改动本身的叙事仍要主管读。

派工失败时，前两次算任务可修，修完重新派工，worker 在同一棵树上接着改；第三次进 `blocked` 交人，不再自动重派。合并之后另说：复跑验收不过就停在 `merge_ready`，由人决定回退还是修复，不自动重试。

这套东西不适合所有场合。改一行文案、需求还没想清、需要你全程做品味判断、跨仓库改动，直接做或先问清楚，派活的开销是收益的十倍。

- 触发：会话里说「用规划与实施分离把 X 落地」或「派 worker 去做」。不说就不派工，通道也不会被探测；判断是否启用看有没有在跑的任务。
- 入口：项目内 `docs/governance/orchestration.md` 是运行期条文正本，本节只讲它由什么构成、为什么这么切。

代价：编排通道要另装（hcom 或 Orca，属 Ask-first 事项）；主管仍是单点，任务拆得不好会在第三次失败时才暴露；并行改动的合并冲突也得主管处理。

## 解决什么问题

下面九条翻车方式，前八条账是同一笔：同一件事被反复解释、反复推演、反复修；第九条是另一笔账，人和 Agent 的时间互相堵着。每条标了投入和回报的量级，粗算，不是实测。

### 会话一长，Agent 就失忆

上下文满了，开新会话，上周定的方案它一个字不记得。你重新解释，它重新提问，一个下午过去，代码没动几行。

三层记忆对付这个：L1 是 `AGENTS.md`，常驻，只放红线和目录；L2 是 `docs/decisions/`，一个决策一条记录，带理由和被否决的方案；L3 是 `docs/memory/`，当前状态快照加跨会话交接。新会话先读快照，再查决策索引最近三条，然后动手。

每次收尾写十几行交接，换掉的是每次开场重新讲一遍背景的时间。上下文不用记住所有事，只要知道去哪查。

### 决策的理由埋在聊天记录里

"当时为什么用轮询不用 WebSocket？"答案在三天前的对话里，没人翻得动。下个会话的 Agent 看了眼代码，觉得 WebSocket 更优雅，推翻了它，没人意识到这是第二遍。

决策记录强制留痕：决定了什么、为什么、否决了什么、影响哪里。四天实战里这个机制接住了五十四条决策。连没走到决策那一步的调研也有去处：方案比较、根因分析、踩坑发现，落进 `docs/design/` 带上状态标注，下次直接查。

投入是每个决策多写几分钟，省下的是一次架构返工，按天算。

### 规则写了好几遍，互相矛盾

`.cursorrules`、`CLAUDE.md`、copilot 的说明文件，再加一段贴在 prompt 里的。四处规则，改一处漏三处，Agent 读到哪份算哪份。

`AGENTS.md` 是唯一事实来源。规则只收 Agent 读代码发现不了的信息，每行先过一遍：删掉它，Agent 会犯错吗？不会，就删。

维护成本从四处降到一处，省下的是排查"Agent 为什么按旧规则干活"的时间。

### Agent 说"完成了"，其实没跑

"已修复。"测试没跑，lint 没过，类型检查一片红。你信了，合并了，CI 教你做人。

规范写死：提交前检查全部通过，禁止跳过验证宣称完成，必须贴命令输出当证据。测试全绿只证明能跑，不证明对。

代价是每次提交多贴一段输出，换来的是不用替 Agent 的自信做担保。

### 代码改了文档没动，文档之间还互相打架

接口签名变了，`docs/design/` 里还是三个月前的图，Agent 照旧文档写新代码，错得理直气壮。更隐蔽的是文档之间的矛盾：一个决策被推翻了，引用它结论的另外三份文档没人记得改。

同步规则写进流程，复盘信号里加了知识体检：矛盾、过期引用、孤儿文档，查到就修。

改代码时顺手同步一处文档，比事后按过期文档返工便宜。

### 沟通驴唇不对马嘴

Agent 这个会话管某个机制叫 A，下个会话叫 B，你 grep 都对不上。"尽快优化一下"这种话，Agent 和你各自理解成了两件事，返工。

沟通受控的一词一义管前者：概念命名随决策产生，全库沿用，改名要走决策。结论先行、一句一义、模糊量词必须落成具体数字，管后者。

成本是起名时多想一次，回报是三个月后还能 grep 得到。

### AI 生成的代码没人评审就进主干

Agent 十分钟写了五百行，看着挺像回事。没有人类评审，合并，上线，出事。

红线钉死：AI 生成的代码未经评审不得合并或部署，评审由人类或主管 Agent 执行，判据是 diff 加本次改动后的验收输出留证；人类评审的强制项就是 `AGENTS.md` §4 的 Ask-first 清单（跨模块/架构、schema、依赖、CI、删数据、测试不绿仍合并）。认证、加密、输入校验一律用成熟库。

这一条算不出投入产出。省不掉，也别指望自动化替你省；能做的是把"必须人类点头"的范围收窄到那份清单，而不是每次合并都守着。

### 上下文被历史堆满

把所有过往对话堆进上下文，token 烧得飞快，关键信息还被淹没。

记忆按需分层加载：快照只记当前，完成项移交 `docs/progress/` 后即删，开场只读决策索引最近三条，行数和单行长度都有硬上限。

收尾裁一次，下次开场就轻。堆着不裁，每个会话都得背着全部历史。

### 一个会话串行推几件事，决策被占住

你手上有三件事要做，交给 Agent 后它一件件来。第一件跑到一半问你接口怎么定，你回完它继续跑，第二件还在队列里等。半天过去，它产出了两件事，你只做了两次决策，中间的时间都花在等它跑完。

把规划和实施拆开就能并行：主管只拆任务、审结果，worker 在各自的 worktree 里干活。主管派完工就结束回合，等 worker 上报再醒来，这中间可以继续处理别的事。

投入：装一次编排通道（hcom 或 Orca），每个任务多写一张派工单。省下：串行等待的时间，以及"它跑完才发现方向不对"的返工。

## 使用方法

安装技能（一个技能同时提供治理骨架与执行编排，装一份就够）：

```bash
# pi
mkdir -p ~/.pi/agent/skills
cp -r skills/vibe-base ~/.pi/agent/skills/

# codex
mkdir -p ~/.codex/skills
cp -r skills/vibe-base ~/.codex/skills/
```

新项目说一句「初始化项目治理」或「init AGENTS」。vibe-base 的初始化区生成骨架：幂等，不覆盖已有文件；占位符不追问，Agent 在后续开发中获知实际信息后自己回填。

之后不需要你操心运转，技能也只在冷启动这一刻登场。init 生成的骨架是 16 个文件：1 份 `AGENTS.md`、14 份 docs（治理与编排细则 7 份、决策模板与索引 2 份、记忆 2 份、设计/进度/规格的目录说明各 1 份）与 1 个控制面脚本 `scripts/foreman.py`；同时建好空的 `.vibe/` 过程态目录并把忽略规则写进 `.git/info/exclude`。写文档时 AGENTS.md 的指针直达这些细则文件，治理信号出现时走治理细则，行为红线由 AGENTS.md 常驻保证，全程不依赖任何技能被"想起来"，甚至不依赖技能还装着。

决策数到 20 条时，`doctor` 的 `governance-budget` 会提示跑一次复盘；触发信号与 8 个自查问句在项目的 `docs/governance/governance-review.md`，判定和改法都落在项目自己的文档里。

两个能力各有入口。骨架由 `AGENTS.md` 常驻，你不用记；编排在会话里说一句「用规划与实施分离把 X 落地」，主管会读项目内的 `docs/governance/orchestration.md` 并照着走，第一次动手之前先体检环境。

## 好处与代价

好处：新项目冷启动一句话得到一套完整规范；跨会话不失忆、不重复踩坑；需要并行时一句话把活派出去，主管不被单条任务占住；每条规则有证据、能自查、可演化；文档之间的矛盾会被定期体检抓出来。

代价：细则加载和自查会拖慢写作节奏；证据门槛会否决一部分"感觉对"的改进；上下文占用增加小于 100 行。这套体系偏向正确而不是速度，琐碎任务凭判断简化。
