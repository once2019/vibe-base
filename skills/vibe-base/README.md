# vibe-base

给 AI 编程 Agent 用的协作规范，以技能 vibe-base 交付。设计不是拍脑袋来的：主体来自 Karpathy 的三套公开理念，经一个真实项目五十四次决策的实战打磨后固化成型。本文先讲理念，再说它补的是哪一层，然后是具体解决哪些问题、怎么用。

## 三套底层理念

这三套都出自 Karpathy 的公开写作，各管一层：Agent 的行为、知识的积累、沟通的质量。

### Guidelines：治 Agent 写代码的常见病

Karpathy 观察 LLM 写代码的翻车姿势，归结成四条规则：

- 动手前把假设说清楚。多种理解并存时全部摆出来，别偷偷挑一个。
- 只写解决问题的最小代码。没人要的抽象、配置项、"以防万一"的异常处理，一律不加。
- 外科手术式修改。每一行变更都能追溯到用户的请求；不顺手"改进"旁边的代码，既有死代码看见了要说，但不动手删。
- 先定义怎么算完成，再动手。修 bug 就先写复现测试，重构就保证前后测试都绿。

这套东西里更值钱的其实是元设计：规则必须来自实测的失败模式，不能从理想实践往下推；每条规则要配一个能自查的问题（"这行改动是用户要的吗？"）；每条规范要承认自己的代价，比如"偏向谨慎，牺牲速度"。

### LLM Wiki：知识要编译，不要每次现查

大多数人用 LLM 处理文档是 RAG 的路子：问一次，查一次，拼一次，什么都没留下。Karpathy 的说法是反过来——让 LLM 把知识"编译"进一个持续维护的维基。新资料来了不是建索引完事，而是读透、摘要点、更新相关页面、标出新旧矛盾；你查询得到的分析也回填进维基。输入和探索都在复利。

这套模式有三个动作：消化新源，查询回填，定期体检（抓矛盾、过期、孤儿页）。它成立的前提就一条：知识库不是死于没人读，是死于没人维护，而维护恰恰是 LLM 不嫌烦的那部分工作。

### 受控文字：沟通也要有硬约束

空客的维修手册用一套叫 ASD-STE100 的受控英语：句长有上限，一个动词只许一个意思，歧义词禁用。Karpathy 拿它说明一个趋势：LLM 越强，人的工作越往"理解"上移，而理解的介质是可以换的——从受控文字，到图，到交互网页，再到按需生成、用完即弃的讲解视频。

落到编程协作，最直接的是前半段：Agent 跟人的沟通也该受控。同一个概念只许一个名字，一句话只说一件事，"尽快处理"必须换成具体日期。

## 怎么落进体系

三套理念按"红线常驻、细则直达"分层落进体系。行为红线每次会话都生效，不赌语义触发；细则不藏在技能触发链里——init 时细则随骨架实例化到项目 `docs/governance/`，AGENTS.md 的指针指向项目内的细则文件，写文档时一步到位，和技能装没装、装在哪完全无关。

| 理念 | 常驻层（AGENTS.md，每次会话生效） | 细则层（项目 docs/governance/ 实例，由 AGENTS.md 指针直达） |
| --- | --- | --- |
| Guidelines | §3 四条行为规则 | 收录铁律，三条元设计管规则演化 |
| LLM Wiki | §6 文档目录给分析产物留了家 | 回填路由；复盘信号新增知识体检 |
| 受控文字 | §3 沟通受控一行 | 行文受控节 |

有些东西明确不搬。LLM Wiki 的全量目录页在百来个文件的项目里是纯负担；时序日志文件和"快照是状态不是日志"的原则相抵，git log 已经管了时序。缺什么补什么，不整套照搬。

## 它补的是哪一层

人和 Agent 一起干活，出问题的地方大多不在代码里。代码写错，测试和评审还能拦；拦不住的是"上次为什么这么定"没人记得，是"这条规则以哪份为准"说不清。人类团队靠人脑、口头和评审把这些兜住，Agent 没有这份连续性，每次会话都像新人第一天上班，还不记得昨天谈过什么。

这套体系补的就是这一层：把靠人记住的东西写成文件。决策连同被否决的方案一起留档，状态快照只记当下，规则只留一份。Agent 开工前读这几处，等于把团队的交接流程接进了它的工作循环。

省事也省在这里。93 行常驻规则写一次，之后每次会话自动生效；一条决策记录多花几分钟，换掉的是下个会话把同一个问题重新推演一遍。反过来算：不写，当下省几分钟，之后每次会话都要重新解释、重新踩坑。会话开得越多，后者越亏。

边界也说清楚：一次性任务、单人小脚本，这套东西是负担。它回本靠的是同一批上下文被反复使用，项目活得越久、换的会话越多，越划算。

## 解决什么问题

下面八条翻车方式，账是同一笔：同一件事被反复解释、反复推演、反复修。每条标了投入和回报的量级，粗算，不是实测。

### 会话一长，Agent 就失忆

上下文满了，开新会话，上周定的方案它一个字不记得。你重新解释，它重新提问，一个下午过去，代码没动几行。

三层记忆对付这个：L1 是 `AGENTS.md`，常驻，只放红线和目录；L2 是 `docs/decisions/`，一个决策一条记录，带理由和被否决的方案；L3 是 `docs/memory/`，当前状态快照加跨会话交接。新会话先读快照，再查决策索引最近三条，然后动手。

投入：每次收尾写十几行交接。省下：每次开场把背景重新讲一遍的时间。上下文不用记住所有事，只要知道去哪查。

### 决策的理由埋在聊天记录里

"当时为什么用轮询不用 WebSocket？"答案在三天前的对话里，没人翻得动。下个会话的 Agent 看了眼代码，觉得 WebSocket 更优雅，推翻了它，没人意识到这是第二遍。

决策记录强制留痕：决定了什么、为什么、否决了什么、影响哪里。四天实战里这个机制接住了五十四条决策。连没走到决策那一步的调研也有去处：方案比较、根因分析、踩坑发现，落进 `docs/design/` 带上状态标注，下次直接查。

投入：每个决策多写几分钟。省下：一次架构返工，按天算。

### 规则写了好几遍，互相矛盾

`.cursorrules`、`CLAUDE.md`、copilot 的说明文件，再加一段贴在 prompt 里的。四处规则，改一处漏三处，Agent 读到哪份算哪份。

`AGENTS.md` 是唯一事实来源。规则只收 Agent 读代码发现不了的信息，每行先过一遍：删掉它，Agent 会犯错吗？不会，就删。

维护成本从四处降到一处；省下的是排查"Agent 为什么按旧规则干活"的时间。

### Agent 说"完成了"，其实没跑

"已修复。"测试没跑，lint 没过，类型检查一片红。你信了，合并了，CI 教你做人。

规范写死：提交前检查全部通过，禁止跳过验证宣称完成，必须贴命令输出当证据。测试全绿只证明能跑，不证明对。

代价是每次提交多贴一段输出，换来的是不用替 Agent 的自信做担保。

### 代码改了文档没动，文档之间还互相打架

接口签名变了，`docs/design/` 里还是三个月前的图，Agent 照旧文档写新代码，错得理直气壮。更隐蔽的是文档之间的矛盾：一个决策被推翻了，引用它结论的另外三份文档没人记得改。

同步规则写进流程，复盘信号里加了知识体检：矛盾、过期引用、孤儿文档，查到就修。

改代码时顺手同步一处文档，比事后按过期文档返工便宜。

### 沟通驴唇不对马嘴

Agent 这个会话管某个机制叫 A，下个会话叫 B，你 grep 都对不上。"尽快优化一下"这种话，Agent 和你各自理解成了两件事，返工。

沟通受控的一词一义管前者：概念命名随决策产生，全库沿用，改名要走决策。结论先行、一句一义、模糊量词必须落成具体数字，管后者。

成本是起名时多想一次，回报是三个月后还能 grep 得到。

### AI 生成的代码没人评审就进主干

Agent 十分钟写了五百行，看着挺像回事。没有人类评审，合并，上线，出事。

红线钉死：AI 生成的代码未经**评审**不得合并或部署——评审由人类或主管 Agent 执行，判据是 diff 加本次改动后的验收输出留证；**人类评审强制项**就是 `AGENTS.md` §4 的 Ask-first 清单（跨模块/架构、schema、依赖、CI、删数据、测试不绿仍合并）。认证、加密、输入校验一律用成熟库。

这一条算不出投入产出。省不掉，也别指望自动化替你省；能做的是把"必须人类点头"的范围收窄到那份清单，而不是每次合并都守着。

### 上下文被历史堆满

把所有过往对话堆进上下文，token 烧得飞快，关键信息还被淹没。

记忆按需分层加载：快照只记当前，完成项移交 `docs/progress/` 后即删，决策索引只留最近三条文件名，行数和单行长度都有硬上限。快照是状态，不是日志。

收尾裁一次，下次开场就轻。堆着不裁，每个会话都得背着全部历史。

## 使用方法

安装技能（一个技能同时提供治理骨架与执行编排，装一份就够）：

```bash
mkdir -p ~/.pi/agent/skills ~/.codex/skills
cp -r skills/vibe-base ~/.pi/agent/skills/
cp -r skills/vibe-base ~/.codex/skills/
```

新项目说一句「初始化项目治理」或「init AGENTS」。vibe-base 的初始化区生成骨架：幂等，不覆盖已有文件；占位符不追问，Agent 在后续开发中获知实际信息后自己回填。

之后不需要你操心运转，技能也只在冷启动这一刻登场。init 生成的骨架是 18 个文件：9 个治理骨架（含 1 份治理复盘证据）、5 份细则（落在项目 `docs/governance/`）、3 份编排设计文档（`docs/design/`）与 1 个控制面脚本（`scripts/foreman.py`）。写文档时 AGENTS.md 的指针直达这些细则文件，治理信号出现时走治理细则，行为红线由 AGENTS.md 常驻保证——全程不依赖任何技能被"想起来"，甚至不依赖技能还装着。

## 规划与实施分离（同一个技能的第二块能力）

前面的骨架管"怎么记、怎么定"；项目做大了会遇到另一个问题：一个会话里串行推几件事，每件都要等它跑完，期间你没法让它决策别的。这块能力把"规划"和"实施"分开：

人类给目标 → 主管拆任务、写派工单（验收命令先于派工存在）→ worker 在独立 git worktree 里实现 → 主管只信 diff 与验收输出 → 通过则合并、删树、出竣工单，然后继续处理别的事。多个任务可以并行，主管每轮只做一步就结束回合，靠编排通道（hcom 或 Orca）唤醒。

- 触发：会话里说一句「用规划与实施分离把 X 落地」「派 worker 去做」。不说就不启用——`.vibe/` 不会存在，通道不会被探测。
- 入口：项目内 `docs/governance/orchestration.md`（条文正本），控制面是 `scripts/foreman.py`（纯标准库）。
- 与骨架的接缝：过程态在 `.vibe/`（本地忽略、不入库、合并后归档），归档后唯一事实源是 `docs/progress/` 的竣工单；Ask-first 裁决必须同时落 `docs/decisions/`，`review` 会拦住缺决策记录的合并；`docs/memory/` 由主管独占写，worker 只写代码。

代价：编排通道要另装（hcom 或 Orca，属 Ask-first 事项）；多任务并行时主管仍是单点，拆解不当会把问题推到第 3 次失败才暴露。

## 好处与代价

好处：新项目冷启动一句话得到一套完整规范；跨会话不失忆、不重复踩坑；每条规则有证据、能自查、可演化；文档之间的矛盾会被定期体检抓出来。

代价：细则加载和自查会拖慢写作节奏；证据门槛会否决一部分"感觉对"的改进；常驻 93 行占的是每次会话的注意力。这套体系偏向正确而不是速度，琐碎任务凭判断简化。


## 这个模板长这样，是复盘出来的

模板在真实项目实战一周（54 条决策）后做了一轮治理复盘：8 个反模式（入口膨胀、压行不压量、规则相抵、决策无索引、Ask-first 散落、易腐运行态、bootstrap 膨胀、不可测触发）各有实测证据与改法，已全部固化进模板本体。证据与自查清单见 `skills/vibe-base/assets/docs/design/governance-retrospective.md`。

## 这个模板不做什么

不规定技术栈，不替你写代码，不保证 Agent 不出错。它只解决"人和 Agent 如何跨会话协作"这一层：记忆不丢、决策可查、规则唯一、验证留证、沟通无歧义。代码质量由你的评审把关，这是红线里唯一不能被自动化替代的部分。
